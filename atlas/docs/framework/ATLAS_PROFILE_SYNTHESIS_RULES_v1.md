# ATLAS Profile Synthesis Rules v1

## 1. Purpose

This document defines the synthesis rules for `profile.md` in Atlas jurisdiction packages.

`profile.md` synthesizes upstream canonical package layers.

`profile.md` translates structured interpretation into jurisdiction posture summaries.

`profile.md` does not introduce new classification authority.

`profile.md` does not introduce new evidence.

`profile.md` does not modify topology placement.

`profile.md` does not change lifecycle status.

Profile is a synthesis layer.

It exists to express interpretive posture in narrative form without altering canonical structure or authority boundaries.

## 2. Profile Authority Boundary

`profile.md` may:
- summarize evidence posture
- summarize signal trajectory
- summarize trust stability
- summarize adjacency dependence
- summarize interpretation continuity

`profile.md` must not:
- introduce corridor attachment claims
- introduce anchor equivalence claims
- modify the topology trio
- replace interpretation boundary language
- promote lifecycle stage

Profile is interpretive synthesis.

It is not a classification engine, authority upgrade, or lifecycle promotion mechanism.

## 3. Profile Synthesis Inputs

`profile.md` may synthesize only from:
- `metadata.md`
- `evidence.md`
- `signals.md`
- `trust-dimensions.md`
- `change-log.md` normalization explanations

`profile.md` must not synthesize from external narrative assumptions.

All synthesis must remain canonically grounded.

If an interpretation cannot be traced to upstream canonical package materials, it does not belong in `profile.md`.

## 4. Evidence Translation Rules

`profile.md` may:
- summarize infrastructure presence
- summarize classification support basis
- summarize corridor participation posture

`profile.md` must not:
- invent infrastructure presence
- reinterpret absence signals as deployment presence
- replace scope boundary language

Profile may condense evidence meaning into readable jurisdiction posture.

It may not transform absence into presence or ambiguity into establishment.

## 5. Signal Translation Rules

`profile.md` may:
- summarize pipeline trajectory
- summarize adjacency strengthening
- summarize readiness indicators
- summarize transition signals

`profile.md` must not:
- treat signals as classification authority
- treat signals as deployment completion
- promote signals into topology placement

Signals remain supportive interpretive inputs.

Profile may narrate their direction.

Profile may not turn them into settled authority.

## 6. Trust Translation Rules

`profile.md` may:
- summarize constraint visibility
- summarize boundary clarity
- summarize adjacency dependence
- summarize interpretation continuity

`profile.md` must preserve trust dimension meaning.

`profile.md` must not introduce scoring language.

Profile may simplify trust presentation into synthesized narrative form, but it must preserve the governing trust posture carried by the upstream trust layer.

## 7. Topology Preservation Rules

`profile.md` must:
- preserve topology trio meaning
- respect completion-layer semantics
- preserve classification source logic
- maintain interpretation boundary visibility

`profile.md` must not:
- introduce alternate corridor roles
- reinterpret completion-layer semantics
- create cross-foundation placement authority

Profile may describe topology posture.

It may not redefine topology schema.

## 8. Adjacency Visibility Rules

`profile.md` may:
- explain adjacency participation pathways
- summarize multi-jurisdiction continuity
- summarize cross-border participation logic

`profile.md` must not:
- convert adjacency into anchor equivalence
- remove adjacency dependence visibility
- replace interpretation boundary constraints

Adjacency may be synthesized narratively.

Its limits must remain visible.

## 9. Lifecycle Interaction Rules

`profile.md` may:
- describe maturity posture
- describe normalization completeness
- describe classification stability

`profile.md` must not:
- promote lifecycle status
- replace metadata lifecycle declaration
- infer lifecycle advancement

Profile may describe the posture associated with lifecycle maturity.

It may not change lifecycle authority or substitute for explicit metadata status.

## 10. Constraint Propagation Rules

`profile.md` must preserve visibility of:
- deployment absence
- policy exclusions
- scope narrowing
- resource constraints
- federal reliance

Constraint visibility must remain intact after synthesis compression.

If synthesis makes a jurisdiction look cleaner but less bounded than the upstream package, the synthesis is non-compliant.

## 11. Interpretation Boundary Preservation Rules

`profile.md` must preserve:
- non-establishment language
- adjacency limits
- classification exclusions
- federal reliance boundaries
- scope narrowing statements

Profile synthesis must not weaken interpretation boundary clarity.

Boundary language may be compressed.

It may not be erased, softened, or replaced by more expansive claims.

## 12. Profile–Builder Mode Interface

`profile.md` provides the interpretive posture input surface for `builder-mode.md`.

`builder-mode.md` may extend profile interpretation into deployment posture discussion.

`profile.md` must not:
- anticipate builder recommendations
- introduce deployment prescriptions
- replace builder-mode reasoning

Profile defines how the jurisdiction reads.

Builder Mode defines what that posture means for builder-facing interpretation.

## 13. Renderer Interaction Rules

The renderer may:
- compress profile summaries
- reorder profile subsections
- surface profile highlights

The renderer must not:
- strengthen classification claims
- remove interpretation boundary visibility
- introduce synthesis not present in canonical files

Renderer normalization may improve readability.

It may not increase profile authority beyond the canonical synthesis contract.

## 14. Profile Compliance Definition

A jurisdiction package is profile-compliant when all of the following are true:
- profile synthesis remains canonically grounded
- topology trio is preserved
- adjacency dependence is visible
- trust dimensions are preserved
- constraint visibility is preserved
- interpretation boundaries are preserved

Non-compliance occurs when any of the following are true:
- profile introduces classification claims
- profile replaces evidence authority
- profile weakens boundary clarity
- profile promotes lifecycle status
- profile converts signals into placement authority
