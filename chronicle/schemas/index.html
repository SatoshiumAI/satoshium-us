Chronicle · Schemas

Satoshium Chronicle Schemas

Chronicle Schemas define the machine-readable structures used to represent canonical Chronicle Entries and supporting Chronicle-owned records. They provide the structural language required for consistency, validation, interoperability, versioning, and long-term preservation.

Chronicle schemas operate within the Satoshium Schemas Standard and should remain compatible with Suite-wide expectations for shared objects, stable identifiers, required fields, metadata, validation-ready records, and schema evolution.

Suite Alignment

Chronicle Schemas implement the Satoshium Schemas Standard within Chronicle. They should follow Suite expectations for common record models, required fields, validation rules, schema evolution, stable identifiers, and machine-readable records.

Authority Boundary

Chronicle schemas define Chronicle-owned objects only. A Chronicle schema may reference an external authoritative object, but it does not redefine the Certification Package, SREG, Integrity Reference, Discovery Signal, Trust Statement, Workflow Definition, Atlas record, or other Suite-owned structure.

Canonical Structure

The Chronicle Base Schema defines the common structure required for canonical Chronicle Entries. Specialized Event-Type Profiles may extend that base with additional requirements without creating competing canonical Entry objects.

Traceability

Structured fields should preserve identifiers, provenance, relationships, authoritative references, evidence links, verification state, corrections, and version lineage so Chronicle records remain reconstructable over time.

Interoperability

Chronicle schemas support reference-based interoperability by representing durable references to authoritative Suite objects without duplicating or redefining the schemas owned by Certifier, Registry, Atlas, Anchor, Beacon, Attestor, Navigator, or other Suite systems.

Schema Evolution

Chronicle schemas should be versioned, extensible, and historically preserved. Schema changes must remain traceable so older Chronicle Entries continue to be understandable and valid under the schema version that governed them.

Validation

Schemas define the structure against which Chronicle records can be validated. Validation rules determine whether required fields, identifiers, controlled values, relationships, references, and other structural requirements are met before publication or other operational use.

Controlled Relationships

Relationship fields should use stable, controlled values where direction or meaning matters. Schema structure should make those relationships machine- readable without implying unsupported causation or authority transfer.

Chronicle Base Schema

The Chronicle Base Schema should define only the universal fields required by every production Chronicle Entry. It is the canonical structural contract for the Chronicle Entry model.

Identity · Event / Occurrence Classification · Temporal Context · Originating System · Authoritative References · Historical Context · Relationships · Provenance · Verification / Validation State · Status · Version / Correction Lineage

Required, conditional, and optional fields should be formally defined once the Entry Model and Identifier Architecture are settled.

Event-Type Profiles

Event-Type Profiles extend the Chronicle Base Schema for specific classes of preserved occurrences. A profile may add required fields, controlled values, authoritative-reference rules, relationship constraints, or validation requirements that apply only to that event class.

The Certification Event-Type Profile is expected to be the first operational profile. It should extend the Base Schema without duplicating the authoritative Certification Package.

Base Schema + Event-Type Profile = Specialized Chronicle Entry

Controlled Values

Controlled values should be governed separately from structural schema definitions where practical. Schemas reference approved vocabularies for fields such as Event Type, Entry Status, Relationship Type, Verification State, Publication State, Correction Type, and other enumerated concepts.

This separation allows terminology to remain governed and interoperable without forcing unnecessary structural schema changes.

Schema Relationships

Chronicle schemas should form a layered architecture rather than a linear chain of co-equal record types. The Base Schema defines the common Entry structure; Event-Type Profiles specialize it; supporting schemas document distinct Chronicle-owned functions.

Chronicle Base Schema → Event-Type Profile → Supporting Chronicle Schemas → Validation → Publication / Preservation

Schema, Validation, and Publication

Schema defines structure. Validation determines whether a Chronicle record conforms to that structure and to applicable controlled values, references, relationships, and operational rules. Publication determines whether a valid record is approved for public production use.

Schema ≠ Validation ≠ Publication

Schema Versioning and Compatibility

Every production Chronicle Entry should remain associated with the schema version that governed it. Schema evolution should define compatibility, deprecation, migration, and preservation rules so historical Entries remain interpretable without silently rewriting older structures.

Schema Philosophy

Schemas should define structure without determining historical conclusions or assuming authority that belongs to another Suite system. Their purpose is to make Chronicle records portable, reviewable, machine-readable, validatable, and durable.

The goal is not schema proliferation. The goal is one coherent structural language with the minimum extensions necessary for Chronicle's institutional responsibilities.
