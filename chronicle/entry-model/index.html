Chronicle Entry Model

The Chronicle Entry Model defines the canonical conceptual structure of a Chronicle Entry before that structure is implemented in formal schemas.

The model establishes which logical components every Entry must contain, which components become required only under defined conditions, and which components remain optional when they add meaningful historical context.

Canonical Principle

A Chronicle Entry is the canonical historical-preservation object of Chronicle. It represents one qualifying historical Occurrence.

Occurrence → Preservation Eligibility → Chronicle Entry

The Entry Model defines the conceptual anatomy of that canonical object. It does not yet freeze field names, identifier formats, controlled values, machine-readable schema syntax, or final validation rules.

Component Requirement Classes

Required → present in every production Chronicle Entry
Conditional → required when a defined circumstance applies
Optional → permitted when historically useful but not universally necessary

Optional does not mean unimportant. It means the component is not universally applicable to every Chronicle Entry.

Identity

Establishes the stable identity of the Chronicle Entry and distinguishes it from every other Chronicle-owned record.

Identity conceptually includes the Entry identifier, Entry title or label, governing schema version, and Entry version.

Required

Event Representation

Describes the qualifying Occurrence being preserved: what happened, what changed, or what historically significant state or milestone the Entry represents.

Required

Temporal Information

Preserves when the underlying Occurrence happened and distinguishes that time from when Chronicle created, validated, published, corrected, or versioned the Entry.

Required

Event Type

Classifies the Occurrence using an approved Chronicle Event Type and determines whether an Event-Type Profile applies.

Required

Historical Context

Explains why the Occurrence matters and provides the surrounding institutional, temporal, relational, or historical context needed to understand it.

Required

Source Record References

Connects the Entry to Chronicle Source Records documenting where supporting information originated.

Conditional

Relationships

Connects the Entry to other Chronicle Entries, supporting Chronicle records, authoritative Suite objects, or other referenced records when those relationships are historically meaningful.

Conditional

Provenance

Documents how information, authoritative references, Sources, Evidence, or other material originated, moved, and entered Chronicle.

Required

Evidence

Connects the Entry to Evidence Records or other approved Evidence structures that support, challenge, contradict, clarify, corroborate, contextualize, or limit confidence.

Conditional

Verification

Records Chronicle's review of its own historical representation, including verification state, review context, limitations, and applicable references.

Required

Version

Identifies the preserved state of the Chronicle Entry and supports traceable lineage when the Entry changes over time.

Required

Correction History

Connects the Entry to Correction Records and prior or resulting versions when Chronicle has materially corrected its own historical record.

Conditional

Publication State

Identifies the Entry's state within Chronicle's publication process and distinguishes publication from Verification, Validation, lifecycle, and preservation state.

Required

Lifecycle / Status

Represents the Entry's institutional state within Chronicle's own lifecycle, independent of the lifecycle or status of the underlying object preserved by the Entry.

Required

Required Components

Every production Chronicle Entry should contain the conceptual components needed to identify the Entry, represent the Occurrence, establish time, classify the event, explain historical context, preserve provenance, support review, maintain version lineage, and express publication and lifecycle state.

Identity · Event Representation · Temporal Information · Event Type · Historical Context · Provenance · Verification · Version · Publication State · Lifecycle / Status

Conditional Components

Conditional components become required when the nature of the Entry, its Event-Type Profile, its history, or its supporting material makes them applicable.

Source Record References · Relationships · Evidence · Correction History

An Event-Type Profile may convert a normally conditional component into a required component for that Event Type.

Optional Components

Optional components may be added when they improve historical understanding without being universally required across all Chronicle Entries.

Examples may later include supplemental notes, public-facing summaries, interpretive context, archival annotations, display metadata, or other approved extensions.

Optional components must not redefine the canonical object or bypass required structure.

Authority Within the Entry

A Chronicle Entry may reference authoritative records from other Suite systems, but those references do not transfer institutional authority to Chronicle.

Chronicle owns the Entry.
The originating system owns the authoritative external object.
Reference does not transfer authority.

Event Date and Entry Dates

The Entry Model must preserve the distinction between the time of the underlying Occurrence and Chronicle's own recordkeeping actions.

Event Date ≠ Entry Creation Date ≠ Publication Date ≠ Correction Date ≠ Version Date

This distinction is essential for retrospective preservation.

Entry Model and Schemas

The Entry Model defines the logical structure first. The Chronicle Base Schema will later translate that model into formal fields, required properties, data types, controlled values, relationships, and machine-readable validation rules.

Entry Model → Base Schema → Event-Type Profile → Production Chronicle Entry

Entry Model Principle

Every Chronicle Entry should contain enough structure to remain identifiable, understandable, traceable, reviewable, correctable, versioned, and preservable across time.
