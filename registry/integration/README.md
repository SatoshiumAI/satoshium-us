# Satoshium Registry Integration

**Institutional interoperability framework for Satoshium Registry**

This directory contains the public documentation and supporting materials for Satoshium Registry Integration.

Registry Integration defines how Satoshium Registry receives, validates, catalogs, references, and maintains authoritative records created by other Satoshium Suite institutions.

Registry creates the SREG.

The originating institution retains authority over the Source Record.

---

## Purpose

The purpose of Registry Integration is to establish a consistent institutional process for connecting Registry with the authoritative records produced throughout the Satoshium Suite.

Registry Integration ensures that records can become:

- identifiable;
- classifiable;
- referenceable;
- version-aware;
- relationship-aware;
- publicly discoverable;
- interoperable across institutions;
- preservable through lifecycle change.

Integration must strengthen institutional separation rather than blur it.

---

## Constitutional Position

Registry Integration operates beneath the Satoshium Suite constitutional hierarchy:

```text
Suite Standards
  ↓
Suite Methodology
  ↓
Suite Interoperability
  ↓
Registry Integration
  ↓
Satoshium Registry Entry (SREG)
```

### Suite Standards

Define shared expectations for terminology, schemas, governance, versions, evidence references, trust references, and interoperability.

### Suite Methodology

Defines documented, repeatable, reviewable, and maintainable implementation principles.

### Suite Interoperability

Defines how institutions exchange identifiers, references, relationships, and metadata without transferring authority.

### Registry Integration

Applies those Suite-wide foundations through Registry intake, validation, SREG construction, publication, lifecycle, and preservation.

---

## Primary Principle

Each Satoshium Suite institution owns its own canonical object and remains authoritative for the records it creates.

Registry is authoritative for the SREG.

The Source Institution is authoritative for the Source Record.

```text
Atlas creates intelligence.
Certifier creates certifications.
Registry creates SREGs.
Chronicle creates historical events.
Anchor creates integrity references.
Beacon creates discovery signals.
Attestor creates trust statements.
Navigator creates workflow definitions.
```

Interoperability connects these objects.

It does not merge institutional responsibilities.

---

## Canonical Integration Model

Registry uses the following integration model:

```text
Source Institution
  ↓
Authoritative Source Record
  ↓
Registry Intake
  ↓
Satoshium Registry Entry (SREG)
  ↓
Public Registry Catalog
```

### Source Institution

The institution that creates and maintains the Source Record.

### Authoritative Source Record

The record owned and controlled by the Source Institution.

### Registry Intake

The Registry process through which the Source Record is identified, reviewed for registrability, classified, referenced, and prepared for SREG creation.

### SREG

The Registry-owned canonical catalog object.

### Public Registry Catalog

The human-readable and machine-readable publication environment through which the SREG becomes discoverable.

---

## Registry Integration Method

Registry applies the following intake process:

```text
Identify or Receive Source Record
  ↓
Confirm Source Institution and Authority
  ↓
Determine Registrability
  ↓
Assign Registry Record Type
  ↓
Assign Registry Identifier
  ↓
Create Source and Relationship References
  ↓
Construct SREG
  ↓
Validate Schema and Terminology
  ↓
Publish
  ↓
Maintain Lifecycle, Versions, Corrections, and Archival Continuity
```

---

## Intake Sources

Registry may identify or receive Source Records through:

- direct institutional handoff;
- approved repository publication;
- approved public reference;
- machine-readable feed;
- Navigator-coordinated workflow;
- documented Registry review;
- another approved interoperability channel.

Regardless of intake method, Registry must preserve:

- Source Institution identity;
- Source-System Identifier;
- canonical source reference;
- source-record version;
- source-record status;
- institutional authority.

---

## Registrability

A Source Record may be registrable when:

- an identifiable Source Record exists;
- the Source Institution can be identified;
- sufficient provenance is available;
- an approved Registry Record Type applies;
- required references exist;
- the proposed SREG can satisfy applicable schema and policy requirements;
- publication is consistent with Suite Standards and institutional boundaries.

Registrability does not imply:

- certification;
- attestation;
- endorsement;
- verification;
- legal recognition;
- ownership;
- regulatory approval.

---

## Registry Responsibilities

Registry Integration is responsible for:

- confirming the Source Institution;
- preserving the Source-System Identifier;
- preserving the canonical source reference;
- determining registrability;
- assigning the Registry Record Type;
- assigning the Registry Identifier;
- constructing the SREG;
- creating typed relationships;
- separating Registry Status from Source-Record Status;
- preserving applicable versions;
- validating schema and terminology;
- publishing human-readable and machine-readable forms;
- maintaining lifecycle, corrections, supersession, revocation, and archival continuity.

---

## Source Institution Responsibilities

The Source Institution remains responsible for:

- Source Record content;
- Source-System Identifier;
- source-record version;
- source-record status;
- institutional meaning;
- outcomes or determinations contained in the record;
- source publication;
- source corrections;
- source retirement or revocation;
- ownership and rights associated with the Source Record.

Registry may report or reference source-controlled values.

Registry does not redefine them.

## Certifier Integration

The first operational Certifier-to-Registry relationship follows this path:

```text
Atlas Resource
  ↓
Certifier Evaluation
  ↓
Certification Package
  ↓
SCRD
  ↓
SREG
```

### Certification Package

Certifier's canonical certification object.

### SCPR

The Certification Process Report documenting the evaluation process.

### SCR

The Certification Receipt documenting certification issuance and public reference information.

### SCRD

The structured Certified Record produced and owned by Certifier.

### SREG

The Registry-owned entry that catalogs the certification record.

Certifier controls certification meaning and status.

Registry controls the SREG and Registry-owned metadata.

## Identifier Mapping

Registry Integration must preserve both Registry and source identifiers.

```text
Registry Identifier
  = identifies the SREG

Source-System Identifier
  = identifies the Authoritative Source Record
```

These identifiers must remain distinct.

A Registry Identifier does not replace:

- a Certification Identifier;
- a Certification Package identifier;
- an SCRD identifier;
- an Atlas resource identifier;
- a Chronicle event identifier;
- an attestation identifier;
- another Source-System Identifier.

---

## Status Mapping

Registry Status and Source-Record Status remain separate across integrations.

Example:

```text
Certification Outcome: Certified
Certification Status: Revoked
Registry Status: Active
```

In this example:

- Certifier has revoked the certification;
- Registry retains the SREG as an active historical catalog entry;
- the SREG accurately reports the source condition;
- discoverability and historical continuity remain preserved.

---

## Version Mapping

Registry Integration must distinguish among:

- Registry Entry Version;
- SREG schema version;
- Record-Type Profile version;
- Registry specification version;
- Source-Record version;
- Source Institution publication version;
- applicable Suite Standards version;
- applicable Suite Methodology version.

These version layers are not interchangeable.

A Source Record may change without the SREG schema changing.

A SREG may be corrected without the Source Record changing.

## Validation Boundaries

Registry validates Registry structure and integration requirements.

Registry may confirm:

- the Source Record exists or is historically documented;
- the Source Institution is identified;
- the Source-System Identifier is preserved when available;
- the Registry Record Type is valid;
- required references exist;
- relationships are structurally valid;
- status values are separated;
- version metadata is complete;
- the SREG conforms to the applicable schema;
- human-readable and machine-readable forms agree.

Registry validation does not replace:

- certification;
- attestation;
- integrity verification;
- historical interpretation;
- source authority;
- legal verification;
- ownership determination.

## Publication Consistency

Human-readable and machine-readable forms of the same SREG must agree on:

- Registry Identifier;
- Registry Record Type;
- Source Institution;
- Source-System Identifier;
- Authoritative Source Record;
- Registry Status;
- Source-Record Status;
- versions;
- relationships;
- public references;
- lifecycle history.

Integration is incomplete when official Registry formats materially disagree.

---

## Source Changes

When a Source Record changes, Registry may update the SREG to reflect:

- new source version;
- changed source status;
- changed canonical location;
- new relationships;
- retirement or revocation;
- supersession;
- archival information.

Registry should preserve:

- prior SREG version;
- prior Source-Record version;
- date and reason for update;
- replacement source reference;
- resulting lifecycle impact;
- correction or version history.

The source change and Registry update must remain distinguishable.

---

## Integration Does Not

Registry Integration does not:

- allow Registry to certify;
- allow Registry to create attestations;
- allow Registry to rewrite Source Records;
- allow Registry to replace Source-System Identifiers;
- allow Registry to absorb institutional authority;
- allow one institution to operate another institution's canonical object;
- convert registration into endorsement;
- convert registration into verification;
- create legal recognition;
- create ownership;
- erase provenance.

Integration connects responsibilities.

It does not erase boundaries.

Integration does not by itself create:

- certification;
- attestation;
- verification;
- ownership;
- legal rights;
- regulatory approval;
- endorsement;
- affiliation;
- source authority.
