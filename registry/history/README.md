# Satoshium Registry History

## Overview

The `registry/history/` directory contains the public institutional page and supporting documentation for the Satoshium Registry History framework.

The public page is published through:

```text
registry/history/index.html
```

This `README.md` serves as the directory-level documentation for that page.

---

## Purpose of This Directory

The purpose of this directory is to define how Satoshium Registry preserves the chronological, versioned, attributable, and resolvable history of:

- Satoshium Registry Entries;
- Registry Identifiers;
- Source Authority reviews;
- Registrability decisions;
- Record-Type assignments;
- relationships;
- provenance;
- Validation;
- Publication;
- Registry Entry Versions;
- Corrections;
- Registry Status;
- Registry Lifecycle;
- Catalog releases;
- Policies;
- Procedures;
- Governance Decisions;
- controlled values;
- schemas;
- Record-Type Profiles;
- restrictions;
- withdrawals;
- archival and preservation actions.

Registry History allows the institution to show not only what a record is now, but how it became what it is.

---

## Constitutional Position

Registry History operates across the complete Registry lifecycle.

```text
Registry Action
  ↓
Versioned Record
  ↓
Historical Event
  ↓
Preserved Timeline
  ↓
Current and Prior States
```

Current state explains what Registry recognizes now.

History explains how that state was reached.

---

## Core Principle

```text
Current state shows what the Registry recognizes.
History shows how the Registry arrived there.
Preservation keeps both accountable.
```

Every material Registry change should be attributable, chronologically placed, version-aware, and historically resolvable.

## Why History Matters

Registry decisions, versions, corrections, and lifecycle transitions become trustworthy only when their sequence and authority remain reconstructable.

History supports:

- accountability;
- institutional memory;
- version continuity;
- correction transparency;
- source attribution;
- lifecycle interpretation;
- Governance review;
- historical discovery;
- archival preservation;
- current-state verification.

## History Characteristics

### Chronological

Events and states are placed in a clear temporal sequence.

### Attributable

Material changes identify authority, process, date, and supporting record.

### Resolvable

Prior states remain accessible through stable identifiers and historical paths.

### Non-Destructive

New states do not erase prior states or material institutional decisions.

### Version-Aware

History preserves the versions of records, schemas, profiles, Rules, Policies, Procedures, and Controlled Values that applied.

## Relationship to Chronicle

Registry History and Chronicle are related but distinct.

Registry History preserves the institutional history of Registry objects and Registry decisions.

Chronicle creates and preserves historical event records within Chronicle's own authority.

Material Registry events may be represented in Chronicle.

Chronicle references may point back to Registry History Records.

```text
Registry owns Registry History.
Chronicle owns Chronicle event records.
```

## Guiding Principles

- Material Registry change should create accountable history.
- History must remain chronological.
- History must remain attributable.
- Prior states must remain resolvable.
- New states must not erase prior states.
- Current and historical materials must remain distinguishable.
- Registry History and Source-System history must remain separate.
- Registry History and Chronicle event records must remain separate.
- History must preserve version context.
- Corrections must preserve the original historical record.
- Restricted history must remain protected.
- Historical artifacts should preserve integrity references when available.
- Governance must control event types and visibility.
- Human-readable and machine-readable History Records must agree.
- Institutional memory is part of Registry durability.
