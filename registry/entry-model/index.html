Satoshium Registry Entry Model

The Registry Entry Model defines the canonical object preserved by the Satoshium Registry: the Satoshium Registry Entry, or SREG.

Registry entries answer a simple question: how should an authoritative record be cataloged?

What Is an SREG?

An SREG is a Satoshium Registry Entry. It is the Registry’s primary operational artifact: a cataloged, version-aware, publicly referenceable entry that preserves the existence, status, relationships, and source references of an authoritative record.

Why Registry Creates SREG

Registry creates SREG entries so authoritative records produced elsewhere in the Satoshium Suite can be discovered, referenced, related, and preserved without transferring authority away from the system that created them.

Canonical Object

Certifier’s canonical object is the Certification Package. Registry’s canonical object is the SREG.

Registry Catalogs

Registry does not certify, score, validate evidence, or alter certification outcomes. Registry catalogs records and preserves their discoverability.

Core Relationship

The architectural relationship between Certifier and Registry is intentionally direct. Certifier produces the certification. Registry catalogs the resulting public certified record.

Certification Package → SCRD → SREG

The Certification Package remains the canonical certification. The SCRD is the public Certified Record produced by Certifier. Registry receives the SCRD and creates an independent SREG Registry Entry.

Registry References Rather Than Duplicates

An SREG may reference a Certification Package, SCRD, source system, public page, receipt, attestation, or related Registry Entry. It does not become those records.

Registry references authoritative records. It does not duplicate them, replace them, or claim ownership over their authority.

This preserves provenance, reduces ambiguity, prevents record drift, and allows each Suite system to maintain its own responsibility.

Registry Identifier

Every SREG has a Registry Identifier that uniquely identifies the entry within the Registry.

Record Type

Every SREG identifies the type of record being registered, such as a certified record, jurisdiction record, media record, tool record, or future supported record class.

Source System

Every SREG identifies the system that produced the source record, such as Certifier, Atlas, Chronicle, Anchor, Beacon, Attestor, Navigator, or an approved external source.

Source Record

Every SREG references the authoritative source record being cataloged. Registry preserves the reference without taking ownership of the source.

Status and Version

Every SREG preserves status and version information so Registry entries can remain understandable as records evolve over time.

Relationships

Every SREG may preserve relationships to packages, receipts, attestations, source records, public references, other Registry Entries, and future Suite objects.

Expected Registry Entry Fields

The final machine-readable schema will be defined separately. At this stage, the Registry Entry Model introduces the expected conceptual fields that every SREG should preserve.

Registry Identifier · Record Type · Source System · Source Record · Status · Version · Relationships · Public References · Registration Date · Last Updated

Long-Term Discoverability

SREG entries allow records to remain findable after public pages move, schemas mature, systems evolve, or new Suite tools are introduced.

Registry becomes the catalog layer that helps the Satoshium Suite remember where records came from, what they reference, and how they relate to the broader ecosystem.

Future Interoperability

Because SREG entries preserve identifiers, statuses, source systems, relationships, public references, registration dates, and update history, they can support future interoperability across Certifier, Chronicle, Anchor, Beacon, Attestor, Navigator, Atlas, and external systems.

Registry preserves records. Registry does not create their authority.
