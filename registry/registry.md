# Satoshium Registry

## Institutional Overview

Satoshium Registry is the authoritative public catalog of institutional records created throughout the Satoshium Suite.

Registry identifies, classifies, references, connects, and preserves the discoverability of authoritative source records through the canonical Satoshium Registry Entry, or SREG.

Registry does not replace the source records created by other Suite institutions. It preserves the public path back to those records while maintaining clear institutional ownership and authority boundaries.

---

## Constitutional Position

Registry operates within the governing architecture of the Satoshium Suite:

```text
Suite Standards
  ↓
Suite Methodology
  ↓
Suite Interoperability
  ↓
Registry Institutional Implementation

Satoshium Registry Entry (SREG)
```

### Suite Standards

Suite Standards define the shared expectations that Registry must satisfy, including requirements for:

- terminology;
- schemas;
- versions;
- governance;
- interoperability;
- evidence references;
- trust references;
- public accountability.

### Suite Methodology

Suite Methodology defines the shared implementation principles used to create documented, reviewable, repeatable, and maintainable institutional processes.

Registry applies those principles through Registry-specific policies and procedures.

### Suite Interoperability

Suite Interoperability defines how Registry exchanges identifiers, references, relationships, and metadata with other Suite institutions without merging institutional responsibilities.

### Registry Institutional Implementation

Registry implements the Suite foundations through:

- Registry Rules;
- Registry Policies;
- Registry Procedures;
- Registry schemas;
- Registry Record Types;
- Registry identifiers;
- Registry lifecycle controls;
- Registry versioning;
- Registry corrections;
- Registry relationships;
- public Registry Entries.

## Mission

The mission of Satoshium Registry is to provide the durable public catalog that connects authoritative records across the Satoshium Suite while preserving:

- institutional ownership;
- source authority;
- stable identification;
- controlled classification;
- public discoverability;
- relationship continuity;
- version history;
- long-term interoperability.

Registry organizes relationships between authoritative records.

Registry does not create the authority contained within those records.

- integrity references;

Without a dedicated catalog, those records may become difficult to:

## Canonical Operational Hierarchy

Registry is organized around a four-layer model:

```text
Satoshium Registry
  ↓
Registry Entry (SREG)
  ↓
Registry Record Type
  ↓
Authoritative Source Record
```

### Satoshium Registry

The institution responsible for the public catalog.

### Registry Entry (SREG)

The canonical operational object of Registry.

A SREG is an independently maintained Registry record that identifies, classifies, references, and connects an authoritative source record.

### Registry Record Type

The controlled primary classification assigned to a SREG.

The Record Type determines how the SREG is organized, validated, displayed, and related to other records.

### Authoritative Source Record

The record created and maintained by the originating institution.

Examples include:

- Certification Package;
- SCRD;
- Atlas canonical jurisdiction record;
- Chronicle historical event;
- Anchor integrity reference;
- Beacon discovery signal;
- Attestor trust statement;
- Navigator workflow definition;
- tool publication;
- media resource.

Registry catalogs the Authoritative Source Record.

Registry does not replace it.

## Authority Boundaries

Each Satoshium Suite institution remains authoritative for the records it creates.

Registry is authoritative for Registry-owned information, including:

- Registry Identifier;
- Registry Record Type;
- Registry Status;
- Registry Lifecycle State;
- Registry Entry Version;
- Registry relationships;
- Registry correction history;
- Registry publication history;
- Registry catalog presentation.

The Source Institution remains authoritative for:

- source-record content;
- source-record identifier;
- source-record version;
- source-record status;
- certification outcome;
- attestation result;
- historical event content;
- integrity reference;
- discovery signal;
- jurisdiction intelligence;
- workflow definition.

Registry may report or reference those source-controlled values.

Registry does not redefine them.

## Satoshium Registry Entry

Every operational Registry record is represented through a SREG.

A SREG should preserve, at minimum, the following conceptual information:

- Registry Identifier;
- Registry Record Type;
- title or recognized name;
- Source Institution;
- Authoritative Source Record;
- Source-System Identifier;
- source-record version;
- source-record status;
- Registry Status;
- Registry Lifecycle State;
- Registry Entry Version;
- applicable schema version;
- public references;
- relationships;
- registration date;
- last updated date;
- correction history;
- supersession information;
- revocation information;
- archival information.

The published Registry schema defines the authoritative field names, validation requirements, permitted values, and structural rules.

## Core Functions

Registry performs several institutional functions.

### Identification

Registry establishes that a SREG exists and assigns it a stable Registry Identifier.

Identification applies to the SREG.

It does not replace the Source-System Identifier.

### Classification

Registry assigns the SREG to an approved Registry Record Type.

Classification supports organization, validation, discoverability, and interoperability.

### Cataloging

Registry publishes the SREG as part of the public Registry catalog.

Cataloging makes the entry discoverable without taking authority away from the source institution.

### Reference Preservation

Registry preserves durable references to the Authoritative Source Record and related institutional objects.

### Relationship Mapping

Registry records typed relationships among SREGs, Source Records, institutions, schemas, events, integrity references, signals, attestations, and workflows.

### Lifecycle Management

Registry maintains the institutional condition of the SREG through registration, activation, update, supersession, revocation, and archival.

### Versioning

Registry preserves distinctions among Registry Entry versions, schema versions, Registry specification versions, and Source Record versions.

### Corrections

Registry documents changes to Registry-owned information while preserving correction history and source authority.

### Preservation

Registry preserves identity, references, relationships, versions, and historical context for future discovery.

## Registrability

A source record may be registrable when:

- an identifiable authoritative source record exists;
- the Source Institution can be identified;
- the source record has sufficient provenance;
- an approved Registry Record Type applies;
- required public or durable references exist;
- the SREG can satisfy applicable schema, terminology, and policy requirements.

Registrability does not imply:

- certification;
- attestation;
- endorsement;
- legal recognition;
- government registration;
- regulatory approval;
- ownership.

## Registry Status

Registry Status describes the current institutional condition of a SREG within Registry.

Registry Status is distinct from:

- Certification Outcome;
- Certification Status;
- Attestation Status;
- Source-Record Status;
- Source Institution status.

Example:

```text
Certification Outcome: Certified
Certification Status: Revoked
Registry Status: Active
```

The SREG may remain active as a public historical catalog entry while accurately reporting that the certification itself has been revoked.

## Registry Lifecycle

Initial lifecycle states include:

- Pending Registration;
- Registered;
- Active;
- Updated;
- Superseded;
- Revoked;
- Archived.

These states are not necessarily a single mandatory linear sequence.

### Pending Registration

The proposed entry has been identified but not formally entered into Registry.

### Registered

The SREG has been created and assigned a Registry Identifier.

### Active

The SREG is the current discoverable Registry representation of the Source Record.

### Updated

Registry-owned information associated with the SREG has been revised.

### Superseded

The SREG or a specific SREG version has been replaced by a newer entry or version while remaining preserved.

### Revoked

The SREG has been withdrawn from active Registry recognition for a documented reason.

### Archived

The SREG is no longer in active operational use but remains preserved as part of Registry history.

Archived does not mean deleted.

## Versions

Registry distinguishes among:

- Suite Standards version;
- Suite Methodology version;
- Registry specification version;
- SREG schema version;
- Record-Type Profile version;
- individual SREG version;
- Source-Record version.

These version layers must remain independently traceable.

A Source Record may change without the SREG schema changing.

A SREG may be corrected without the Source Record changing.

A schema may evolve while older SREGs remain preserved under their original schema version.

## Corrections

Registry corrections apply to Registry-owned information.

Corrections may address:

- identifiers;
- titles;
- classifications;
- references;
- relationships;
- dates;
- version metadata;
- source locations;
- Registry Status;
- formatting;
- structural errors;
- schema compliance.

Material corrections should document:

- what changed;
- why it changed;
- when it changed;
- which version was affected;
- which version replaced it.

Registry must not silently rewrite the content or authority of a Source Record.

## Interoperability

Registry follows the Suite Interoperability principle that every institution owns its own canonical object.

A typical certification relationship is:

```text
Atlas Resource
  ↓
Certifier Evaluation
  ↓
Certification Package
  ↓
SCRD
  ↓
SREG
```

The Certification Package remains Certifier's canonical certification object.

The SCRD remains a Certifier-owned certified record.

The SREG remains Registry's canonical catalog entry.

Interoperability connects institutional objects through identifiers, references, relationships, and compatible schemas.

It does not merge institutional authority.

Registry may catalog or preserve references to:

- evidence resources;
- attestations;
- trust statements;
- integrity references;
- public verification locations.

- confirming that the referenced source exists;
- confirming the Source Institution;
- confirming the Source-System Identifier;
- confirming that the Record Type is valid;
- confirming schema compliance;
- confirming that references and relationships are structurally valid.

Certifier evaluates certification evidence.

Attestor creates trust statements and attestations.

Anchor preserves integrity references.

Registry catalogs the resulting records and relationships.

## Disclaimer

Satoshium Registry is an informational public-record and catalog institution.

A SREG documents Registry identifiers, classifications, references, relationships, versions, lifecycle information, and status metadata based on authoritative source records and available information at the time of registration or update.

A Registry Entry does not by itself create:

- ownership;
- legal rights;
- certification;
- attestation;
- verification;
- source authority;
- intellectual-property rights;
- financial standing;
- regulatory approval;
- historical truth.

Those forms of authority remain with the applicable Source Institution, Source Record, governing authority, rights holder, or responsible external system.
