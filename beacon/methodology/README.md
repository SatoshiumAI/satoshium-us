# Satoshium Beacon — Discovery Methodology

## Overview

The **Beacon Discovery Methodology** defines the repeatable institutional process by which an observed candidate may become a governed Satoshium Beacon Discovery Signal, progress through review and publication, and remain maintained over time.

The governing principle is:

> **Discovery becomes institutional only through a preserved and reviewable process.**

The methodology is derived from Beacon's Phase II production architecture rather than imposed independently upon it.

---

# Methodological Inquiry

The preliminary process proposed for Beacon was:

```text
Observe
→ Identify
→ Source
→ Evaluate Relevance
→ Construct Metadata
→ Validate
→ Publish
→ Maintain
```

This sequence captured the broad direction of Beacon's work, but Phase II inquiry showed that it compressed several institutionally distinct acts.

In particular:

```text
Identification
≠ canonical creation

Construction
≠ canonical creation

Validation
≠ lifecycle transition

Lifecycle transition
≠ publication

Publication
≠ creation of a second canonical object
```

Earlier Beacon architecture established that the canonical Discovery Signal must exist before object-level Validation can occur.

Therefore the preliminary sequence is not adopted verbatim.

---

# Methodological Finding

The Phase II architecture supports the following institutional sequence:

```text
Candidate Observation
        ↓
Candidate Identification
        ↓
Source & Provenance Establishment
        ↓
Relevance Assessment
        ↓
Discovery Signal Construction
        ↓
Canonical Creation & BEAC Assignment
        ↓
Validation & Institutional Review
        ↓
Lifecycle Determination
        ↓
Publication Decision
        ↓
Public Representation
        ↓
Maintenance & Re-observation
```

In concise form:

> **Observe → Identify → Establish Source & Provenance → Assess Relevance → Construct → Create → Validate & Review → Determine State → Decide Publication → Represent → Maintain**

This preserves the useful intent of the preliminary proposal while aligning each stage with Beacon's established institutional architecture.

---

# Why Observation Comes First

Beacon cannot institutionally represent a discovery before potentially relevant information, an object, condition, event, or relationship has first been encountered.

Observation may occur through:

```text
human review

Beacon process

Navigator-directed workflow

governed system interaction

other permitted discovery context
```

However:

```text
Observation
≠
Discovery Signal
```

Observation produces a potential candidate.

It does not itself create a canonical Beacon object.

---

# Why Identification Remains Pre-Object

Identification occurs when Beacon recognizes that an observation may represent a distinct candidate discovery worth further consideration.

This remains a pre-object condition.

Conceptually:

```text
Observed
→ potentially relevant information encountered

Identified
→ candidate discovery recognized

Created
→ canonical Discovery Signal exists
```

Therefore:

```text
Identified
≠
Created
```

This preserves the lifecycle distinction established earlier in Phase II.

---

# Why Creation Must Be Explicit

The Discovery Signal Lifecycle established that canonical Creation is the event at which the Beacon object comes into existence.

At Creation:

```text
canonical Discovery Signal exists

BEAC identifier is assigned

Lifecycle State → Draft

Publication State → Unpublished
```

Therefore Validation cannot precede canonical Creation when Validation is evaluating the Beacon object itself.

The sequence must preserve:

```text
Candidate
        ↓
Construction
        ↓
Creation
        ↓
BEAC Identifier
        ↓
Draft Discovery Signal
        ↓
Validation
```

# Canonical Methodology

The Beacon Discovery Methodology consists of eleven stages:

```text
1. Observe

2. Identify

3. Establish Source & Provenance

4. Assess Relevance

5. Construct

6. Create

7. Validate & Review

8. Determine State

9. Decide Publication

10. Represent

11. Maintain
```

These stages form the baseline institutional production process for Beacon Discovery Signals.

---

# Stage 1 — Observe

Beacon encounters potentially relevant:

```text
information

object

condition

event

relationship
```

The observation should preserve enough context to support later provenance if the candidate progresses.

Observation may be:

```text
human initiated

Beacon-process initiated

Navigator-directed

workflow generated

other governed discovery activity
```

At this stage:

```text
no canonical Discovery Signal exists

no BEAC identifier exists
```

---

# Stage 2 — Identify

Beacon determines whether the observation presents a distinct candidate discovery worth further consideration.

The result is:

```text
Identified Candidate
```

Identification means the observation warrants further institutional inquiry.

It does not mean:

```text
the discovery is true

the candidate is relevant enough for canonicalization

the source has been verified

a Discovery Signal exists

publication is warranted
```

---

# Stage 3 — Establish Source & Provenance

Beacon must establish both:

```text
Source Identity

and

Discovery Provenance
```

These are related but distinct.

## Source

Source answers:

```text
What did Beacon observe?
```

Relevant source information may include:

```text
source identity

source institution / publisher

native identifier

source object type

source location

source-native status
```

when applicable.

## Provenance

Provenance answers:

```text
How did Beacon encounter and preserve the observation?
```

Relevant provenance may include:

```text
observation time

observation method

observation context

supporting basis

discovery actor or process
```

The distinction remains:

```text
Source
→ what was observed

Provenance
→ how Beacon encountered it
```

---

# Provenance Chain

Conceptually:

```text
Source / Authoritative Object
        ↓
Observation
        ↓
Discovery Context
        ↓
Candidate Discovery
        ↓
Beacon Discovery Signal
        ↓
Preserved Provenance
```

If the candidate cannot support meaningful source identification or provenance, it may stop, defer, or require further review rather than automatically progressing.

---

# Stage 4 — Assess Relevance

Beacon determines whether the candidate belongs within Beacon's institutional responsibility for:

```text
Discovery & Signals
```

The relevance inquiry asks whether Beacon has a legitimate institutional reason to represent the candidate as discovery.

Conceptually:

```text
Candidate is relevant to Beacon's discovery role
+
sufficient basis exists to continue
=
proceed to construction
```

A candidate that does not meet Beacon's relevance threshold should not be forced into a Discovery Signal.

---

# Relevance Is Not Truth

Relevance assessment does not establish:

```text
truth

Certification

Registry standing

historical significance

Integrity verification

Trust
```

It determines whether the candidate is appropriate for Beacon's discovery role.

Therefore:

```text
Relevant to Beacon
≠
authoritatively true
```

---

Construction may include:

```text
Discovery Metadata

Canonical References
```

as applicable.

Conceptually:

```text
=
constructable Discovery Signal
```

Construction prepares the institutional representation.

It does not itself create the canonical object.

---

# Stage 6 — Create

Creation is the explicit institutional event at which the canonical Discovery Signal comes into existence.

At Creation:

```text
Candidate representation
        ↓
Canonical Discovery Signal
        ↓
BEAC-YYYY-NNNN assigned
        ↓
Lifecycle State → Draft
        ↓
Publication State → Unpublished
```

The BEAC identifier is:

```text
permanent

assigned at Creation

assigned before object-level Validation

not reused
```

Creation establishes Beacon ownership of the Discovery Signal.

It does not transfer ownership of any referenced source object.

---

# Stage 7 — Validate & Review

The created Draft Discovery Signal is evaluated against Beacon's established conformance requirements and institutional boundaries.

Validation may include:

```text
Canonical Identity

BEAC Identifier conformance

required Entry Model components

permitted Signal Type

Source identification

Provenance sufficiency

Canonical Reference integrity

Discovery Metadata sufficiency

Timestamp conformance

Status conformance

Version conformance

Relationship conformance

Schema conformity

Authority-boundary review
```

---

# Validation Outcome

Initial Phase II architecture recognizes outcomes such as:

```text
Valid

Invalid

Review Required
```

Whether these become exact machine values remains subject to implementation.

Passing Validation establishes:

```text
eligibility for institutional progression
```

It does not itself establish:

```text
truth

publication

Active lifecycle state

source authority

Certification

Registry standing

Integrity verification

Trust
```

---

# Validation and Institutional Review

Validation and institutional review are related but not necessarily identical.

Validation primarily evaluates conformance.

Institutional review may require judgment concerning:

```text
relevance

provenance sufficiency

authority boundaries

relationship meaning

publication suitability

restrictions

exceptions
```

A schema-valid object is not automatically an institutionally publishable Beacon Discovery Signal.

---

# Stage 8 — Determine Lifecycle State

Passing Validation does not itself perform a lifecycle transition.

Beacon must apply the appropriate governed institutional state.

The normal initial progression is:

```text
Draft
        ↓
governed transition
        ↓
Active
```

Later maintenance may result in:

```text
Superseded

Resolved

Withdrawn
```

according to Beacon Lifecycle and Versioning & Supersession architecture.

---

# Stage 9 — Decide Publication

Publication is a separate governed decision.

The architecture preserves:

```text
Canonical existence
≠
Validation
≠
Active lifecycle state
≠
Publication
```

A valid Active Discovery Signal may remain:

```text
Unpublished
```

when publication is restricted, deferred, or not approved.

---

# Publication Eligibility

A Discovery Signal may become eligible for publication when:

```text
Canonical identity exists
+
BEAC identifier conforms
+
Entry Model requirements are satisfied
+
Validation passed
+
Lifecycle State permits publication
+
public provenance is sufficient
+
authority boundaries are preserved
+
references are attributable
+
relationships are attributable
+
no governing restriction prevents publication
=
Eligible for Publication Decision
```

Eligibility does not itself publish the Discovery Signal.

Publication remains an institutional act.

---

# Stage 10 — Represent

When publication is approved:

```text
Publication State
→ Published
```

Beacon then exposes the Discovery Signal through its Records architecture.

Conceptually:

```text
Published Discovery Signal
        ↓
/beacon/records/
        ↓
Beacon Records listing

and

/beacon/records/BEAC-YYYY-NNNN/
        ↓
permanent individual Beacon Record
```

The Beacon Record is the canonical public HTML representation of the Discovery Signal.

It does not create a second canonical object.

# Stage 11 — Maintain

Beacon's institutional responsibility does not end when a Discovery Signal is published.

Maintenance includes:

```text
preserving the original observation

preserving provenance

re-observing sources when appropriate

recording source availability changes

correcting presentation defects

versioning material canonical changes

creating new signals for institutionally distinct discoveries

preserving supersession relationships

applying Resolved state when appropriate

applying Withdrawn state when appropriate

keeping Beacon Records consistent with canonical objects
```

Maintenance preserves institutional continuity over time.

---

# Re-observation

A later observation must not silently rewrite an earlier one.

The governing distinction is:

```text
What Beacon observed then
≠
What Beacon observes now
```

Re-observation may support:

```text
new version

new Discovery Signal

resolution

supersession

withdrawal

continued confirmation

additional context
```

depending on the institutional meaning of the later observation.

---

# Correction

A presentation-only defect may be corrected without unnecessarily changing the canonical Discovery Signal.

Conceptually:

```text
HTML presentation error
+
canonical Discovery Signal remains correct
=
presentation correction
```

A material error in the canonical object itself is governed by Beacon Versioning & Supersession.

---

# Version

A material change to the representation of the same canonical Discovery Signal may require a governed new version.

Conceptually:

```text
BEAC-2026-0001 v1
        ↓
material revision
        ↓
BEAC-2026-0001 v2
```

The BEAC identifier remains stable because the canonical Discovery Signal remains the same institutional object.

---

# New Discovery Signal

A new BEAC identifier should be used when the later discovery is institutionally distinct.

Potential examples include:

```text
distinct discovery subject

distinct occurrence

distinct relationship

independently meaningful discovery
```

A new discovery should not be forced into an existing Discovery Signal merely to preserve identifier continuity.

---

# Stop Conditions

The methodology must permit a candidate to stop without becoming a canonical Discovery Signal.

Potential stop, defer, or escalation conditions include:

```text
insufficient relevance

source cannot be meaningfully identified

provenance is inadequate

candidate duplicates an existing discovery without new institutional meaning

Beacon lacks a legitimate basis to represent the discovery

additional review is required
```

The governing principle is:

> **Not every observation deserves canonicalization.**

This prevents Beacon from treating mere visibility as institutional significance.

---

# Authority Throughout the Process

Authority boundaries apply from Observation through Maintenance.

The methodology preserves:

```text
Observe a source

own the source

≠
inherit its authority

Publish a Discovery Signal
≠
certify the source assertion
```

The governing Suite principle remains:

> **Reference does not transfer authority.**

# Governing Rules

Beacon Discovery Methodology follows these rules:

```text
Observe before canonicalizing.

Identify the candidate.

Identify the source.

Preserve provenance.

Assess relevance without claiming truth.

Construct according to the Entry Model.

Create the canonical object explicitly.

Assign the BEAC identifier at Creation.

Enter Draft at Creation.

Remain Unpublished until publication occurs.

Validate the created object.

Preserve institutional review separately where judgment is required.

Govern lifecycle transitions separately from Validation.

Govern publication separately from lifecycle state.

Preserve authority boundaries.

Publish a representation, not a second canonical object.

Maintain history after publication.

Preserve later observations without rewriting earlier ones.

Permit candidates to stop when Beacon lacks sufficient basis.
```

The governing principle is:

> **Discovery becomes institutional only through a preserved and reviewable process.**
