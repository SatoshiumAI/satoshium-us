## 1. Purpose

The Satoshium Suite Reconciliation exists to reconcile the completed operational Satoshium Suite into one internally consistent institutional architecture.

The reconciliation examines the Suite as it now exists and identifies, evaluates, and deliberately resolves or preserves:

- contradictions;
- ambiguity;
- stale assumptions;
- terminology collisions;
- overlapping authority;
- inconsistent object definitions; and
- unresolved Suite-level architectural questions.

The objective is coherence, not redesign.

The reconciliation is complete only when the formal Suite can be described through one internally consistent model of institutions, authority, canonical objects, relationships, lifecycle semantics, controlled terminology, and operational status.

---

## 2. Scope

This reconciliation applies to the formal Satoshium Suite.

The formal Suite consists of eight institutions:

1. **Atlas** — Authoritative Intelligence
2. **Navigator** — Workflow Definition / Orchestration

6. **Anchor** — Integrity Reference
7. **Beacon** — Discovery Signal / Discovery Metadata
8. **Attestor** — Attestation + Rule-Constrained Evaluation + Trust Statement

All eight institutions are Operational.

The reconciliation may address:

- institutional roles;
- institutional authority;
- canonical responsibilities;
- canonical object ownership;
- terminology;
- relationship semantics;
- lifecycle semantics;
- publication semantics;
- provenance;
- correction and supersession;
- Suite-level architecture;
- conceptual sequence;
- distinctions among institutions;
- legacy architecture where it conflicts with the current operational institutional architecture;
- stale current-state documentation that directly affects Suite coherence;
- unresolved Suite-level ambiguities;
- necessary Suite-level reconciliation decisions.

## 4. Governing Methodology

The reconciliation follows a preservation-first methodology.

The preferred order of action is:

**CONFIRM → CLARIFY → RECONCILE → CORRECT → CHANGE**

A change to functioning architecture should occur only when the existing architecture cannot remain internally coherent without that change.

### 4.1 Issue-by-Issue Discipline

Substantive reconciliation questions shall be handled one issue at a time.

For each substantive issue requiring a decision:

1. State the issue.
2. Present the relevant existing architecture and evidence.
3. Identify the contradiction or ambiguity.
4. Explain available interpretations where necessary.
5. Recommend the best reconciliation.
6. Explain the reasoning.
7. Obtain approval before establishing a decision that materially affects Suite architecture.

Once approved, a decision is treated as established for the remainder of the reconciliation unless later evidence creates a genuine contradiction.

Routine documentation corrections that merely implement an already-settled decision do not require repeated approval.

### 4.2 Historical Discipline

The reconciliation distinguishes:

1. historically accurate descriptions of an earlier state; from
2. stale current-state statements that are now false.

Historical records shall be preserved.

Current documentation shall be corrected where necessary.

The reconciliation shall not:

- retroactively describe an institution as Operational before it became Operational;
- rewrite historical production artifacts merely to make later architecture appear cleaner; or
- erase valid historical terminology solely because later architecture matured.

## 5. Evidence Standard

Reconciliation decisions shall be grounded in the strongest available existing Satoshium evidence.

Evidence may include:

- current governing documentation;
- institutional landing pages;
- canonical object records;
- published production artifacts;
- controlled-value definitions;
- current repository documentation;
- approved prior architectural decisions;
- preserved historical records where historical context is relevant;
- first production relationships and exercised lineage;
- explicit current institutional status.

Evidence shall be interpreted according to its actual authority and context.

### 5.1 Evidence Rules

The following disciplines apply:

- current-state documentation does not override a stronger canonical object or approved architectural decision merely because it is easier to find;
- historical records shall not be treated as current architecture when the architecture has since matured;
- referenced objects do not transfer their authority to the referencing institution;
- exercised production lineage demonstrates relationships but does not automatically establish a mandatory universal pipeline;
- institution-specific controlled vocabularies shall not be generalized Suite-wide without reconciliation establishing that they are genuinely Suite-wide.

Where evidence conflicts, the reconciliation shall identify the conflict explicitly rather than silently choosing one source.

## 7. Decision Classes

The reconciliation may use the following decision classes.

### CONFIRMED

Existing architecture is internally coherent and remains authoritative without modification.

### CLARIFIED

Existing architecture remains valid, but wording, scope, or boundaries require explanation to eliminate ambiguity.

### RECONCILED

Two or more existing descriptions, concepts, or architectural elements require a deliberate harmonized interpretation in order to remain coherent.

### CORRECTED

A current-state statement, document, label, status, or representation is stale or inconsistent with already-established architecture and must be corrected.

### CHANGED

Existing functioning architecture must be modified because internal coherence cannot otherwise be maintained.

This class should be used sparingly.

### RESERVED

An issue is intentionally left open because the current Suite does not require a final resolution and no material contradiction results from preserving it.

### DEFERRED

An issue belongs to a later review or broader scope and is handed forward explicitly.

Deferred issues should identify their destination where possible, including:

- **Interoperability Review**
- **Satoshium Universe Documentation Reconciliation**

### HISTORICAL — PRESERVE

The material accurately represents an earlier state and should remain unchanged as historical documentation.

## 8. File Handling Rule

When repository files are provided during reconciliation:

1. Read the complete file.
2. Compare the complete file against architecture already established in the reconciliation.
3. If a required correction is routine, current-state, and supported by settled decisions, update the file proactively.
4. Provide the finished updated file.
5. If the file exposes a substantive architectural question, stop before silently resolving it.
6. Present the architectural issue for reconciliation.
7. After approval, update the affected file.

File review shall not be limited only to the sentence or issue that caused the file to be provided.
