## Purpose

This record consolidates the semantic boundaries that must survive future Satoshium Suite development.

These distinctions are not optional editorial preferences.

They are architectural safeguards established through the September 25–30, 2026 Suite Reconciliation to prevent future development from collapsing institutional roles, canonical object identity, authority, provenance, lifecycle, relationship semantics, or governed outcomes.

The governing principle is:

> **Future implementation may extend the Suite, but it must not silently erase the distinctions that make the Suite coherent.**

---

# 1. Connection ≠ Identity

A relationship between two objects does not make them the same object.

```text
Connection
≠ Identity
```

Cross-institution references, workflow participation, production lineage, discovery, preservation, registration, integrity protection, and evaluation do not merge canonical identities.

---

# 2. Reference Does Not Transfer Authority

This is the strongest Suite-wide authority rule.

> **REFERENCE DOES NOT TRANSFER AUTHORITY.**

A referencing institution may identify, consume, preserve, evaluate, discover, register, or coordinate around another institution's object without becoming authoritative for that object.

---

# 3. Reference ≠ Derivation ≠ Support

The relationship vocabulary must remain semantically distinct.

```text
references
→ points to / identifies

derived-from
→ establishes lineage / origin

supports
→ provides evidentiary or logical support
```

Therefore:

```text
Reference ≠ Derivation

Reference ≠ Support

Derivation ≠ Support
```

One relationship must not be inferred merely because another exists.

---

# 4. Evaluates ≠ Results-In

```text
evaluates
→ describes an evaluative relationship or process

results-in
→ describes an output-producing relationship
```

A subject being evaluated does not itself become the result.

---

# 5. Supersedes ≠ Corrects

```text
supersedes
→ replaces operative standing while preserving history

corrects
→ repairs an error or defect
```

These relationships are not interchangeable.

---

# 6. Authority ≠ Provenance

```text
Authority
→ who governs, owns, decides, or bears institutional responsibility

Provenance
→ where information originated and how it was obtained, moved, transformed, or preserved
```

Therefore:

> **AUTHORITY ≠ PROVENANCE**

Strong provenance does not create authority.

Authority does not erase provenance.

---

# 7. Ownership ≠ Use

An institution may use another institution's canonical object without owning it.

```text
Input use
≠ ownership

Reference use
≠ authority transfer
```

Cross-institution use must preserve originating authority.

---

# 8. Registration ≠ Source Ownership

Registry creates and governs:

```text
Satoshium Registry Entry (SREG)
```

Registry does not create or become authoritative for the registered source object.

```text
Registry authority
→ SREG

Source authority
→ source institution
```

---

# 9. Historical Preservation ≠ Source-State Control

Chronicle creates and governs:

```text
Chronicle Entry
```

Chronicle preserves qualifying historical Occurrences.

It does not control the current operational state, lifecycle, or substantive determination of the source object.

---

# 10. Integrity Preservation ≠ Source Authority

Anchor creates and governs:

```text
Integrity Reference
```

Anchor establishes integrity within a declared Representation Boundary.

It does not establish:

```text
truth
certification
source meaning
universal completeness
trust authority
```

unless separately and explicitly governed elsewhere.

---

# 11. Discovery ≠ Verification

Beacon creates and governs:

```text
Discovery Signal
```

Discovery may surface an object, condition, state, or change.

Discovery does not certify, verify, validate, or determine the source matter.

---

# 12. Orchestration ≠ Ownership

Navigator creates and governs:

```text
Navigator Workflow Definition
```

Navigator may coordinate work among institutions.

It does not inherit their authority.

```text
Workflow Orchestration
≠ institutional decision ownership
```

---

# 13. Workflow State ≠ Canonical Institutional State

Navigator may maintain workflow-local state.

That state does not become the lifecycle state of the participating institution's canonical object.

```text
Workflow-local state
≠ canonical institutional state
```

---

# 14. Certification ≠ Verification

```text
Verification
→ correspondence / evidence / reference checking

Certification
→ Certifier-governed certification determination
```

Therefore:

> **Verification ≠ Certification**

A verification process does not silently become certification authority.

---

# 15. Eligibility ≠ Validation

```text
Eligibility
→ admission determination

Validation
→ determination against applicable institutional requirements
```

An eligible object may still fail Validation.

A valid object may have entered through an eligibility decision governed separately.

---

# 16. Validation ≠ Conformance

```text
Validation
→ institutional / formal / structural requirement determination

Conformance
→ determination against an explicit requirement set
```

Validation may support Conformance.

Validation is not Conformance.

---

# 17. Validation ≠ Evaluation

```text
Validation
→ checks requirements

Evaluation
→ applies governed rules, criteria, and evidence
```

A valid object is not automatically supported, correct, trustworthy, or favorably evaluated.

---

# 18. Valid ≠ True

This distinction must remain explicit.

```text
Valid
≠ True
```

Validation does not create universal truth authority.

---

# 19. Valid ≠ Supported

```text
Valid
→ satisfies applicable Validation requirements

Supported
→ controlled Evaluation Outcome where defined
```

These remain distinct.

---

# 20. Evaluation ≠ Evaluation Outcome

```text
Evaluation
→ process

Evaluation Outcome
→ controlled result
```

The process and its result must not be collapsed.

---

# 21. Evaluation Outcome ≠ Trust Statement

```text
Evaluation Outcome
→ controlled result

Trust Statement
→ canonical Attestor conclusion
```

A Trust Statement may be based on an Evaluation Outcome, but they are not the same object or semantic layer.

---

# 22. Evaluation ≠ Universal Truth

Attestor performs:

```text
Rule-Constrained Evaluation
```

It does not determine universal truth.

The Attestor model remains:

```text
Eligible Governed Inputs
→ Attestation
→ Rule-Constrained Evaluation
→ Trust Statement
```

The Trust Statement is bounded by:

```text
rules
evidence
scope
provenance
authority context
limitations
```

---

# 23. Attestation ≠ Trust Statement

Attestor has two canonical object families:

```text
Attestation
Trust Statement
```

An Attestation is a governed attributable assertion.

A Trust Statement is Attestor's governed bounded conclusion.

They must remain distinct.

---

```text

→ controlled result
```

Canonical object ownership must remain explicit.

```text

        ↓
Publication
```

But these are distinct acts.

> **CREATION DEFINES EXISTENCE. ACTIVATION DEFINES OPERATIVE STATE. PUBLICATION DEFINES ACCESSIBILITY.**

# 31. Institutional Status ≠ Object Lifecycle State


# 32. Decision / Outcome ≠ Lifecycle State

A decision or outcome may influence a later transition.

It is not itself a lifecycle state.

```text
Decision
≠ Lifecycle State

Evaluation Outcome
≠ Lifecycle State

Certification Outcome

```

---

# 33. Version ≠ Lifecycle State

Version identity and lifecycle state must remain separate.

```text
Version
≠ Active
≠ Published
```

A new Version does not automatically become active or published.

---

# 34. Correction ≠ Version

```text
Correction

```

Therefore:

> **Correction ≠ Version**

---

# 35. Correction ≠ Deletion

Correction must preserve traceability.

```text
Correction
≠ Deletion
```

History should not disappear merely because a record was corrected.

---

# 36. Supersession ≠ Mutation

Supersession changes operative standing while preserving prior identity and history.

```text
Supersession
≠ Mutation
```

The prior object or version is not silently rewritten out of existence.

---

# 37. Changed Conclusion = Changed Canonical Statement

This rule is especially important for Attestor.

> **CHANGED CONCLUSION = CHANGED CANONICAL STATEMENT**

A materially changed assertion or conclusion may require a new canonical identity rather than silent mutation.

---

# 38. Material Change May Require New Identity

A non-material correction may remain within continuity.

A material semantic change may require a new canonical object identity.

This must be determined by the governing institution.

---

# 39. NOT-TESTED ≠ PASS

This rule must survive all executable Validation and Conformance development.

```text
NOT-TESTED
≠ PASS
```

Unknown, untested, or unavailable mandatory evidence must never be silently converted into success.

```text
Interoperability
```

An institution may coordinate with another without becoming structurally dependent on it in every future operation.

---

Future implementation should preserve:

```text
identity
lineage
prior states
correction history
supersession history
```

rather than silently rewriting the record.
