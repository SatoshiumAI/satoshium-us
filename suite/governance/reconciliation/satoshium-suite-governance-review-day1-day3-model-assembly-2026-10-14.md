## Day 1 Core Doctrine

> **One Suite. Eight sovereign institutions. Shared constitutional constraints. Distinct canonical authority. Interaction without authority transfer.**

Suite Governance governs matters that genuinely belong to the Suite as a whole.

Institutional Governance governs matters that remain inside the settled authority of an institution.

The boundary is:

> **Suite Governance governs the boundaries that make the Suite coherent. Institutional Governance governs the work that makes each institution operational.**

# II. Day 2 — Institutional Change & Membership

Day 2 established how the Suite may evolve without casually rewriting itself.

The core principle is:

> **Institutions are free to evolve inside the architecture. They are not free to redefine the architecture.**

---

## Institutional Change

An institutional change is:

> **A governed change that alters the formal identity, settled role, authority boundary, canonical-object ownership, constitutional position, or institutional existence of a Satoshium Suite institution.**

The core threshold is:

```text
CHANGE WITHIN SETTLED AUTHORITY
→ ordinary institutional evolution

CHANGE TO SETTLED AUTHORITY
→ Suite-level architectural change
```

---

## Change-Type Model

Day 2 distinguished:

```text
Documentation Correction
Operational Refinement
Methodology Change
Governance Change
Canonical-Object Change
Institutional-Role Change
Constitutional Change
```

The governing classification principle is:

> **A change is classified according to the highest-order governed subject it actually alters, not according to the file, page, codebase, or repository location where it appears.**

---

## Governance Change Classification Model

The formal three-class model is:

```text
ROUTINE
→ Institution-Level

MATERIAL
→ Institution + Suite Review

CONSTITUTIONAL
→ Formal Suite Governance Decision
```

### Routine

Exercises existing authority.

### Material

Has significant cross-Suite, governance, interoperability, or canonical-architecture consequences without changing the constitutional allocation of role, ownership, sovereignty, or membership.

### Constitutional

Changes foundational Suite architecture.

---

## Existing Institution Change Authority

An institution may:

- expand capabilities within its role;
- narrow nonessential capabilities;
- change Procedures;
- refine Methodology within authority;
- add supporting objects;
- evolve implementation;
- refine canonical schemas while preserving canonical identity.

An institution may not unilaterally:

- change canonical ownership;
- replace canonical object architecture;
- expand into another institution's role;
- transfer authority;
- change formal Suite membership;
- alter institutional sovereignty;
- create mandatory constitutional dependency.

The governing test is:

```text
CHANGE WITHIN AUTHORITY
→ institution may govern

CHANGE TO AUTHORITY
→ Suite Governance must govern
```

---

## Creation of a New Suite Institution

A new formal institution requires:

```text
Demonstrated Need
Unique Responsibility
Non-Duplication
Explicit Authority Boundary
Distinct Canonical Ownership
Interoperability Review
Institutional Sovereignty Review
Constitutional Review
Formal Admission
```

The governing rule is:

```text
NEW CAPABILITY
≠
NEW INSTITUTION
```

---

## Structural Institutional Change

- authority;
- lifecycle;
- correction;
- versioning;
- identifiers;
- interoperability;
- existing records;
- effective date;

The governing preservation rule is:

# III. Day 3 — Governance Process, Decisions, Versioning & Accountability

Day 3 established how governance is exercised over time.

The standard lifecycle is:

```text
Proposal
→ Review
→ Determination
→ Approval
→ Publication
→ Implementation
→ Preservation
```

Classification remains an intake control governing the depth of review.

---

## Governance Roles

The governing rule is:

```text
governed subject
+
change classification
+
affected authority
```

The principal roles are:

```text
Proposer
Reviewer
Determiner
Approver
Implementer
Publisher
```

The separation rules are:

```text
PROPOSER
≠ APPROVER

REVIEWER
≠ DECISION OWNER

IMPLEMENTER
≠ GOVERNANCE AUTHORITY

PUBLISHER
≠ APPROVER
```

Routine matters may combine roles where appropriate.

Material and Constitutional matters require increasing separation and traceability.

---

## Proposal / Decision / Implementation / Documentation

The distinction is:

```text
Governance Proposal
→ asks what should change

Governance Decision
→ determines what is authorized

Implementation Action
→ executes the authorized change

Documentation Update
→ records and communicates the resulting state
```

The precedence rule is:

```text
APPROVED GOVERNANCE DECISION
↓
AUTHORIZED IMPLEMENTATION
↓
CURRENT DOCUMENTATION
```

---

## Review Escalation Thresholds

### Institution-Level Review

Required when the matter affects an institution's own governed domain.

### Suite-Level Review

Required when the matter materially affects:

- another institution;
- shared Standards;
- shared Methodology;
- shared governance;
- canonical architecture;
- Suite-wide coherence.

### Interoperability Review

Required when the matter materially affects:

- exchange;
- interfaces;
- schemas;
- serialization;
- identifiers;
- references;
- provenance;
- state propagation;
- compatibility.

### Architecture Reconciliation

Required when the matter:

- contradicts settled architecture;
- reopens canonical ownership;
- changes institutional role;
- creates unclear authority;
- creates a constitutional dependency;
- conflicts with settled Suite semantics.

The core rule is:

> **Review follows impact.**

---

## Governance Versioning

Governance versioning is:

> **The controlled issuance, identification, supersession, correction, preservation, and historical linking of authoritative governance states over time.**

Core distinctions:

```text
VERSION
≠ DECISION

CORRECTION
≠ VERSION

SUPERSESSION
≠ MUTATION

CHANGED CONCLUSION
=
NEW GOVERNANCE DECISION
```

---

## Supersession

Supersession is:

> **The governed replacement of a prior decision's current operative standing by a later approved governance decision while preserving the prior decision as an intact historical record.**

The model is:

```text
Prior Decision
→ historically valid for its effective period

New Decision
→ controlling prospectively

Relationship
→ SUPERSEDES
```

---

## Governance Corrections

Four correction classes exist:

```text
Erroneous Governance Text
Incorrect Implementation
Obsolete Governance
Conflicting Governance
```

Conflicting governance follows:

```text
CONFIRM
→ CLARIFY
→ RECONCILE
→ CORRECT
→ CHANGE
```

---

## Governance Decision Register

The Suite requires a formal Governance Decision Register.

The distinction is:

```text
GDR
→ authoritative record of one governance decision

Governance Decision Register
→ authoritative index of governance decisions
```

The Register should contain:

- all Material decisions;
- all Constitutional decisions;
- selected significant Routine decisions.

The Register makes current standing, supersession, classification, institutional impact, and canonical-object impact discoverable.

# IV. Transparency & Historical Preservation

The governance model requires two simultaneous views.

## Current-State Governance

Must clearly show:

- current effective governance;
- current versions;
- current authority;
- current decision standing;
- current institutional status.

## Historical Governance

Must preserve:

- prior decisions;
- prior versions;
- former authority states;
- prior architecture;
- corrections;
- supersession;
- transition history.

The two views must not collapse into each other.

The governing preservation rule is:

```text
CURRENT GOVERNANCE
→ may change

HISTORICAL GOVERNANCE
→ must remain true
```
