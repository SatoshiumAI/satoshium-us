## Purpose

This record defines the governance required to create and formally admit a **new Satoshium Suite institution**.

Creation of a new formal institution is a constitutional act because it changes:

- the formal Suite roster;
- the distribution of responsibility;
- the allocation of canonical ownership;
- the authority map;
- and potentially the interoperability model.

Accordingly:

> **A new Suite institution may not arise through documentation, implementation convenience, repeated practice, naming, or de facto operational use. It must be formally justified, architected, reviewed, and admitted.**

---

# Governing Principle

> **Create a new institution only when a genuinely new and durable institutional responsibility cannot be coherently absorbed by the existing Suite without distorting established roles or authority boundaries.**

The default presumption is:

```text
NEW CAPABILITY
≠
NEW INSTITUTION
```

A new institution requires more than:

- a new application;
- a new tool;
- a new service;
- a new interface;
- a new workflow;
- a new data object;
- a new website section;
- a new operational function.

It requires a distinct constitutional responsibility.

---

# 1. Demonstrated Need

## Requirement

A proposal must establish that there is a real, persistent, Suite-level need that existing institutions cannot adequately govern within their settled roles.

The proposal must answer:

```text
What problem exists?

Why is the problem durable rather than temporary?

Why is the need institutional rather than merely operational?

Why can the need not be satisfied through:
→ capability expansion
→ supporting object
→ new Procedure
→ new Methodology
→ interoperability enhancement
→ existing institutional governance
```

## Insufficient Grounds

The following are not sufficient by themselves:

- convenience;
- organizational preference;
- branding;
- repository cleanliness;
- implementation complexity;
- desire for symmetry;
- a new technical subsystem;
- a temporary project;
- workload distribution.

## Determination Standard

```text
Demonstrated need
→ REQUIRED
```

No demonstrated need:

```text
NO NEW INSTITUTION
```

---

# 2. Unique Responsibility

## Requirement

The proposed institution must have a responsibility that is:

- distinct;
- durable;
- governable;
- institution-worthy;
- and not merely a subdivision of an existing role.

The proposed responsibility must answer:

```text
What does this institution exist to do?

Why is that responsibility conceptually distinct?

Why is it not simply:
→ a feature
→ a workflow
→ a profile
→ a service
→ a supporting layer
→ a Procedure
→ an implementation module
```

## Test

A valid institutional responsibility should be expressible in a concise form similar to:

```text
Atlas
→ Authoritative Intelligence

Registry
→ Canonical Registration / Public Catalog

Chronicle
→ Historical Preservation
```

If the proposed responsibility cannot be stated distinctly without borrowing another institution's role, the proposal is not mature enough for institutional admission.

---

# 3. Non-Duplication

## Requirement

The proposed institution must not duplicate existing Suite responsibility.

The review must explicitly compare the proposal against all eight existing institutions:

```text
Atlas
Navigator
Certifier
Registry
Chronicle
Anchor
Beacon
Attestor
```

The proposal must demonstrate that it does not duplicate:

- institutional role;
- canonical responsibility;
- authority boundary;
- lifecycle authority;
- decision authority;
- governance function.

## Duplication Test

Ask:

```text
Can an existing institution perform this responsibility
through ordinary evolution
without changing its constitutional role?
```

If YES:

```text
PREFER EXISTING INSTITUTION
```

If NO:

```text
CONTINUE NEW-INSTITUTION REVIEW
```

## Governing Rule

> **Institution creation is not a substitute for disciplined capability expansion.**

# 4. Authority Boundary

## Requirement

The proposed institution must define precisely what authority it would hold and what authority it would not hold.

Required authority statement:

```text
The institution MAY:
→ ...

The institution MAY NOT:
→ ...
```

The review must establish:

- decision authority;
- source authority boundary;
- lifecycle authority;
- correction authority;
- versioning authority;
- publication authority;
- evaluation or determination authority;
- relationship to Suite Governance.

## Prohibited Admission Pattern

A proposal must fail if its authority is defined mainly by reference to control over other institutions.

Examples:

```text
"approves all Suite institutions"
"validates all institutional decisions"
"controls publication across the Suite"
```

unless the Suite explicitly intends to create such a constitutional authority through formal review.

## Non-Transfer Rule

Admission must preserve:

```text
REFERENCE DOES NOT TRANSFER AUTHORITY

INTEROPERABILITY DOES NOT TRANSFER AUTHORITY

SUITE MEMBERSHIP DOES NOT ERASE INSTITUTIONAL SOVEREIGNTY
```

---

# 5. Canonical Ownership

## Requirement

A formal institution must have a clearly defined canonical responsibility.

The proposal must identify:

- canonical object or object family;
- canonical identifier model;
- lifecycle ownership;
- correction ownership;
- versioning ownership;
- publication ownership;
- provenance expectations;
- relationship semantics.

## Important Constraint

Not every institution must necessarily require multiple canonical objects.

But a formal institution without a distinct canonical responsibility risks becoming merely:

- a service;
- a tool;
- a workflow;
- or a coordination layer.

## Canonical Ownership Test

The proposal must answer:

```text
What object or responsibility is uniquely canonical here?

Why can that canonical ownership not remain
with an existing institution?
```

If no distinct answer exists:

```text
DO NOT CREATE NEW INSTITUTION
```

---

# 6. Interoperability Implications

## Requirement

Before admission, the proposal must assess how the new institution interacts with the existing Suite.

The review must identify:

- upstream references;
- downstream references;
- provenance behavior;
- identifier resolution;
- lifecycle interactions;
- version propagation;
- correction propagation;
- serialization implications;
- dependency implications;
- publication implications;
- whether any existing institution must alter its architecture.

## Critical Test

Ask:

```text
Can the new institution interoperate
without forcing existing institutions
to surrender authority or rewrite their canonical identity?
```

If NO:

```text
ADMISSION SHOULD FAIL OR REQUIRE BROADER CONSTITUTIONAL REDESIGN
```

## Dependency Rule

A new institution may participate in workflows.

It must not automatically become a mandatory constitutional gate.

Any proposed mandatory dependency must be reviewed explicitly as a constitutional issue.

---

# 7. Formal Admission

## Requirement

A proposed institution does not become part of the Suite until formal admission is complete.

Formal admission must include:

```text
1. Proposal
2. Need Analysis
3. Responsibility Definition
4. Non-Duplication Review
5. Authority Boundary Review
6. Canonical Ownership Definition
7. Interoperability Impact Review
8. Governance Review
9. Constitutional Determination
10. Formal Approval
11. Publication
12. Architectural Registration
13. Historical Preservation
```

## Required Admission Record

The admission decision should record at minimum:

- institution name;
- institutional role;
- justification;
- canonical object(s);
- authority boundary;
- prohibited authority claims;
- Suite membership status;
- effective date;
- interoperability dependencies;
- governance owner;
- publication location;
- superseded architectural statements, if any;
- preserved historical record of the prior Suite state.

## Admission Status

Only after formal approval may the institution be described as:

```text
Formal Satoshium Suite Institution
```

Before approval, it remains one of:

```text
External
Experimental
Candidate
Proposed
Pre-Suite
Service
Tool
Subsystem
```

as applicable.

# Rejection Conditions

A proposal should not be admitted if:

- an existing institution can absorb the capability coherently;
- responsibility substantially duplicates an existing role;
- no unique canonical responsibility exists;
- authority boundary is vague;
- the proposal requires silent authority transfer;
- it creates unjustified mandatory dependency;
- it exists primarily for branding or organizational convenience;
- interoperability requires existing institutions to surrender sovereignty;
- the proposal has not passed formal constitutional review.

---

# Relationship to Aegis Precedent

Aegis demonstrates the importance of distinguishing:

```text
important Satoshium system
```

from:

```text
formal Suite institution
```

A system may be architecturally significant, operationally valuable, or historically important without automatically becoming a Suite institution.

Formal Suite membership must therefore be conferred through governance, not inferred from importance or proximity.

# Governing Doctrine

> **A new Suite institution must solve a distinct constitutional problem, not merely provide a new operational capability.**

Expanded:

> **Creation requires demonstrated need, unique responsibility, non-duplication, explicit authority boundaries, distinct canonical ownership, interoperable independence, and formal constitutional admission. No tool, service, subsystem, or repeated practice becomes a Suite institution by implication.**
