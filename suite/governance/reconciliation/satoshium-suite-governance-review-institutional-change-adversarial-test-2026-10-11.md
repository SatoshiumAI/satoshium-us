## Purpose

This record adversarially tests whether the assembled governance model can prevent institutional architecture from changing casually or implicitly.

The test asks:

1. Could a ninth institution be added casually?
2. Could an institution redefine itself through documentation?
3. Could a supporting object quietly become canonical?

The test uses the current public institutional surfaces for Atlas, Certifier, Registry, Chronicle, Anchor, Beacon, Navigator, and Attestor as current-state evidence of the eight-institution architecture and each institution's bounded role.

# II. Attack 1 — Could a Ninth Institution Be Added Casually?

## Attack Scenario A — New Tool Becomes "Institution #9"

A new Satoshium tool becomes:

- operational;
- public;
- important;
- integrated with several institutions;
- separately documented;
- given its own repository and identifier family.

Documentation then begins listing it beside the eight formal institutions.

### Attack Path

```text
New Tool
→ Public
→ Operational
→ Integrated
→ Listed with Suite
→ Treated as Institution #9
```

### Failure Risk

If this succeeds:

```text
operational maturity
→ becomes constitutional membership
```

The formal Suite roster would change without a constitutional decision.

---

## Governing Defense

Day 2 established:

```text
NEW CAPABILITY
≠ NEW INSTITUTION

INTEGRATION
≠ SUITE MEMBERSHIP

OPERATIONAL
≠ SUITE MEMBER

THERE IS NO DE FACTO SUITE MEMBERSHIP
```

Formal admission requires all membership tests:

```text
Demonstrated Need
Unique Institutional Responsibility
Non-Duplication
Distinct Canonical Responsibility
Explicit Authority Boundary
Independent Institutional Sovereignty
Interoperability Without Authority Transfer
Formal Constitutional Admission
```

The Aegis precedent already demonstrates that even a mature, important, integrated Satoshium service may remain external to the formal Suite.

### Determination

```text
ATTACK
→ BLOCKED
```

A ninth institution cannot legitimately arise through:

- branding;
- website placement;
- repository structure;
- operational maturity;
- tooling;
- integration;
- repeated use.

It requires a formal Constitutional Governance Decision.

# XI. Supporting-to-Canonical Test

The adversarial review establishes a precise escalation trigger.

A supporting object does **not** become canonical merely because it gains:

- stable identifier;
- schema;
- lifecycle;
- publication;
- versioning;
- correction;
- external reference.

Those properties may indicate that canonical review is warranted.

They do not themselves create canonical status.

The decisive question is:

> **Has the Suite explicitly recognized the object as carrying independent canonical institutional responsibility?**

If NO:

```text
SUPPORTING
```

If YES through valid governance:

```text
CANONICAL
```

# XIV. Pressure Point Identified

One important pressure point remains inherently future-facing:

> **A supporting object can become operationally sophisticated enough that users begin treating it as canonical before governance has acted.**

The current model blocks this legally/architecturally, but operational discipline is required.

The resulting guardrail is:

```text
IF supporting object develops
independent identity + lifecycle + versioning + publication + authority-like use
→ REQUIRE explicit canonical-status review
```

This is not new architecture.

It is an enforcement trigger for the already-approved supporting-object boundary.
