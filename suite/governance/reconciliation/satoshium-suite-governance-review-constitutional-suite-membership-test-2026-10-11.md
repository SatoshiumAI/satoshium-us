## Purpose

This record defines the constitutional test for determining whether a system qualifies as a **formal Satoshium Suite institution**.

The test distinguishes a formal Suite institution from:

- a service;
- a tool;
- a subsystem;
- an application;
- an external system;
- a pre-Suite system;
- an integration layer;
- or another supporting Satoshium capability.

The central question is:

> **What must be true before a system may legitimately be recognized as a formal Suite institution?**

---

# Constitutional Membership Test

A proposed system qualifies for formal Suite membership only if **all** required constitutional conditions are satisfied.

The test contains eight mandatory elements.

---

## 1. Distinct Institutional Responsibility

The proposed member must have a responsibility that is:

- durable;
- distinct;
- institution-worthy;
- governable;
- not merely technical;
- not merely procedural;
- not merely a supporting capability.

The responsibility must be expressible as a concise institutional role.

Examples from the existing Suite:

```text
Atlas
→ Authoritative Intelligence

Chronicle
→ Historical Preservation

Anchor
→ Integrity Preservation
```

If the proposed system cannot state a distinct institutional responsibility without substantially borrowing another institution's role:

```text
FAIL
```

---

## 2. Demonstrated Constitutional Need

The proposed member must solve a need that cannot be coherently satisfied through:

- capability expansion inside an existing institution;
- a new supporting object;
- a new Procedure;
- a new Methodology;
- a service;
- a tool;
- a subsystem;
- or an interoperability enhancement.

The test is:

```text
Can an existing institution absorb this responsibility
without changing its settled constitutional role?
```

If YES:

```text
NO NEW MEMBER REQUIRED
```

If NO:

```text
CONTINUE TEST
```

---

## 3. Non-Duplication

The proposed member must not duplicate the settled responsibility of:

- Atlas;
- Navigator;
- Certifier;
- Registry;
- Chronicle;
- Anchor;
- Beacon;
- Attestor.

The review must compare:

- role;
- authority;
- canonical responsibility;
- lifecycle authority;
- decision authority;
- publication authority;
- governance function.

Substantial duplication means:

```text
FAIL
```

unless the broader Suite architecture is itself being constitutionally redesigned.

---

## 4. Distinct Canonical Responsibility

The proposed institution must have a clearly defined canonical responsibility.

This should normally include:

- canonical object or object family;
- canonical identity;
- lifecycle ownership;
- correction ownership;
- versioning ownership;
- publication ownership;
- provenance model;
- relationship semantics.

A system that only produces implementation artifacts, logs, reports, dashboards, or service outputs does not thereby satisfy this test.

The key question is:

> **What uniquely canonical responsibility exists here that cannot remain with an existing institution?**

If there is no distinct answer:

```text
FAIL
```

---

## 5. Explicit Authority Boundary

The proposed member must have a precise authority boundary.

The admission record must state:

```text
MAY:
→ ...

MAY NOT:
→ ...
```

The authority model must define:

- what decisions the institution may make;
- what objects it may govern;
- what lifecycle decisions it may control;
- what corrections it may issue;
- what versions it may create;
- what conclusions it may make;
- what authority remains with other institutions.

Vague authority means:

```text
FAIL
```

---

## 6. Independent Institutional Sovereignty

The proposed institution must be capable of exercising its settled responsibility without requiring it to become a subordinate operating arm of another institution.

Likewise, its existence must not require other institutions to surrender sovereignty.

The test asks:

```text
Can this institution operate its own canonical responsibility
without absorbing another institution's authority
or becoming constitutionally dependent on another?
```

If NO:

```text
FAIL OR REQUIRE BROADER CONSTITUTIONAL REDESIGN
```

---

## 7. Interoperability Without Authority Transfer

The proposed institution must be able to interoperate with the existing Suite while preserving:

- institutional identity;
- canonical ownership;
- source authority;
- lifecycle independence;
- provenance;
- existing Suite semantics.

The proposal must demonstrate:

```text
REFERENCE DOES NOT TRANSFER AUTHORITY

INTEROPERABILITY DOES NOT TRANSFER AUTHORITY

MEMBERSHIP DOES NOT ERASE SOVEREIGNTY
```

If membership would require silent authority transfer:

```text
FAIL
```

---

## 8. Formal Constitutional Admission

Even if all architectural tests pass, the system is not a Suite institution until formal admission occurs.

Formal admission requires:

```text
Proposal
→ Review
→ Constitutional Determination
→ Approval
→ Publication
→ Architectural Registration
→ Historical Preservation
```

Before that point, the system remains outside formal membership.

# Institution vs. Service Test

A useful constitutional distinction is:

## Service

A service generally:

- performs a bounded function;
- may expose endpoints or interfaces;
- may support multiple institutions;
- may produce service outputs;
- may be operationally important;
- may be reusable;
- may be deeply integrated.

But it does not necessarily own a distinct constitutional responsibility.

## Institution

An institution:

- has a distinct Suite-level responsibility;
- has bounded authority;
- owns a canonical responsibility;
- has lifecycle authority;
- has correction and versioning authority;
- makes institution-specific decisions;
- is constitutionally recognized;
- is formally admitted.

Therefore:

```text
FUNCTIONAL CAPABILITY
→ may be a Service

CONSTITUTIONAL RESPONSIBILITY
→ may justify an Institution
```

---

# Tool / Subsystem Boundary

A tool or subsystem may:

- implement part of an institution;
- assist multiple institutions;
- provide validation;
- provide inspection;
- provide automation;
- provide transport;
- provide rendering;
- provide monitoring;
- provide testing.

Those functions do not establish membership.

The tool becomes constitutionally relevant only when a proposal seeks to assign it an independent institutional responsibility.

---

# Mandatory Gate Rule

A system does not become an institution merely because it is mandatory in an implementation.

Example:

```text
all institutions use Service X
```

does not imply:

```text
Service X is a Suite institution
```

Technical centrality and constitutional status are different concepts.

# No De Facto Membership Rule

The following cannot create Suite membership:

- time;
- repeated use;
- operational dependence;
- technical centrality;
- repository placement;
- public navigation;
- cross-linking;
- common branding;
- naming convention;
- integration depth;
- production use.

The rule is:

> **Membership must be declared by constitutional governance, never inferred from circumstance.**

# Governing Doctrine

> **A formal Suite institution is not merely a capable system. It is a constitutionally recognized authority with a distinct responsibility, canonical ownership, bounded sovereignty, and formal admission.**
