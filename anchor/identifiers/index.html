Anchor · Identifiers

Satoshium Anchor · Identifiers

Identifier Architecture defines how Anchor gives stable identity to its canonical object: the Integrity Reference.

An Anchor Identifier identifies the Anchor-owned Integrity Reference. It does not replace, reinterpret, or absorb the Source-System Identifier of the authoritative artifact being referenced.

Identifier Principle

Anchor Identifier → Integrity Reference
Source-System Identifier → Source Artifact

These identifiers describe different institutional objects and must remain independently meaningful.

Source-System Identifier ≠ Anchor Identifier

Anchor Identifier

The stable identifier assigned by Anchor to an Integrity Reference. It identifies the Anchor record itself across publication, Verification, Versioning, Corrections, relationships, and long-term preservation.

Architecture Defined

Source-System Identifier

The identifier assigned by the Source Institution to the authoritative artifact referenced by Anchor, such as a Certification Package, Registry Entry, or Chronicle Entry.

External Authority

Source Institution

The institution that governs the Source-System Identifier and the Authoritative Artifact associated with it.

Required Context

Anchor Version

A Version identifies a governed state of the Integrity Reference. Versioning must remain distinct from the identity of the Integrity Reference itself.

The Source-System Identifier identifies the external authoritative object. The Anchor Identifier identifies the integrity-preservation record created for a defined representation of that object.

Identifier Stability

Once assigned to a production Integrity Reference, an Anchor Identifier should remain stable. Corrections, later Verification, maintenance, and other ordinary lifecycle events should not silently change its identity.

Identifier Uniqueness

Every production Anchor Identifier must uniquely identify one Anchor-owned Integrity Reference within the Anchor namespace.

Identifier Immutability

The identifier itself should not be repurposed to identify a different Integrity Reference after publication.

Identifier Persistence

Anchor Identifiers should remain resolvable or reconstructable across long-term publication, archival, migration, and technology change.

Identifier vs. Version

Identifier identity and Version identity are separate concerns.

Anchor Identifier ≠ Anchor Version

A later Anchor Version may remain part of the same Integrity Reference, depending on the Versioning rules established later.

A materially different integrity subject may instead require a new Integrity Reference and therefore a new Anchor Identifier.

Identifier vs. Source Artifact Version

Source-System Identifier ≠ Source Artifact Version ≠ Anchor Identifier ≠ Anchor Version

A Source Institution may revise its artifact without changing the meaning of the original Anchor Identifier. Anchor must preserve which Source representation and Source Version, where applicable, the Integrity Reference actually covered.

Known Suite Examples

Existing Suite identifiers demonstrate the need for explicit cross-system separation.

SC-CERT-2026-0001 → Certifier-owned Certification Package
SREG-2026-0001 → Registry-owned Satoshium Registry Entry
CHR-2026-0001 → Chronicle-owned Chronicle Entry

If Anchor later preserves Integrity References for these artifacts, each Anchor record will receive its own Anchor Identifier.

The existing Source-System Identifier must remain present as the Source reference rather than being replaced by the Anchor Identifier.

Identifier Format

The final Anchor Identifier syntax is intentionally not frozen on this page.

The eventual production format should be evaluated against:

uniqueness · readability · namespace clarity · stable parsing · long-term durability · human recognition · machine interoperability · Version independence · correction safety

Possible syntax should be tested against the Integrity Reference schema and the first production record before adoption.

Format Unfrozen

What the Identifier Must Not Encode Prematurely

The identifier should avoid embedding mutable or interpretive information unless production architecture demonstrates that it is necessary.

Integrity State
Verification Result
Publication State
Lifecycle State
Source Artifact status
trust judgment
certification result
mutable Version metadata

These concepts may change while the identity of the Integrity Reference remains stable.

Identifier Assignment

Production architecture should eventually define the point at which an Anchor Identifier becomes permanently assigned.

Candidate stages include Integrity Reference construction, successful Validation, Publication approval, or another governed production boundary.

That assignment point remains intentionally unfrozen until the Validation and Publication architectures are defined.

Corrections and Identifiers

A Correction should not automatically create a new Anchor Identifier. Later Corrections architecture must determine whether the correction modifies an existing Integrity Reference through Versioning or requires a new Integrity Reference.

Correct forward. Preserve backward.

Relationships and Identifiers

Stable identifiers will allow later Anchor architecture to express relationships precisely.

Integrity Reference → Source Artifact
Integrity Reference → prior Anchor Version
Integrity Reference → Correction
Integrity Reference → superseding Integrity Reference
Integrity Reference → external commitment

This is why Identifier Architecture precedes Relationships, Provenance, Schemas, Versioning, Corrections, and Publication.

Identifier Authority

Anchor governs only the Anchor Identifier namespace.

It does not reinterpret or reassign identifiers owned by Certifier, Registry, Chronicle, Atlas, Beacon, Attestor, Navigator, or external Source Institutions.

Reference does not transfer authority.

Identifier Architecture Principle

Anchor Identifiers should provide stable identity for Integrity References while preserving the independent identity and authority of every Source Artifact.

Identify the Anchor record. Preserve the Source identifier. Never confuse the two.
