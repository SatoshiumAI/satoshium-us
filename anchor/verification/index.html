Satoshium Anchor · Integrity Verification

Integrity Verification defines how Anchor determines whether a Reviewed Representation remains consistent with the Canonical Representation governed by an Integrity Reference.

Verification evaluates integrity consistency. It does not establish truth, certification, trustworthiness, historical meaning, or Source authority.

Architecture Defined

What Verification Proves

A successful Integrity Verification supports the conclusion that the Reviewed Representation remains consistent with the representation governed by the Integrity Reference under the recorded Verification method.

Successful Verification → representation consistency

What Verification Does Not Prove

Integrity Verification ≠ Truth
Integrity Verification ≠ Certification
Integrity Verification ≠ Trust
Integrity Verification ≠ Reputation
Integrity Verification ≠ Historical Interpretation
Integrity Verification ≠ Source Authority

A perfectly preserved artifact may still contain incorrect, outdated, disputed, or low-quality information.

Reviewed Representation

The Reviewed Representation must be evaluated under the same governed boundary used when the Integrity Reference was created.

Different presentation ≠ automatically different representation
Different governed representation = different verification subject

Dynamic interface elements, navigation, timestamps, ads, comments, or other excluded material should not affect Verification if they were outside the original Representation Boundary.

Canonical Reconstruction

Verification may require reconstructing the Canonical Representation from the Reviewed Representation.

Reviewed Representation
↓
apply governed canonicalization rules
↓
Reconstructed Canonical Representation

If the canonicalization rules cannot be reproduced, Verification should not silently guess.

Single-Method Verification

For a single integrity method, Verification may be straightforward:

Reconstructed Canonical Representation
↓
apply recorded method / algorithm
↓
Reproduced Integrity Value
↓
compare with stored Integrity Value

Composite Verification

Where multiple Integrity Methods were used, Verification may need to validate each component and their dependency order.

digest
+ signature
+ timestamp
+ external commitment

Composite Verification should not collapse all components into one opaque result if one component can succeed while another fails or is unavailable.

External Commitment Verification

External commitment methods may require validating historical proof material against the external system.

Integrity Value
↓
external proof material
↓
external system validation
↓
external commitment result

Failure to reach an external service must remain distinguishable from a cryptographic mismatch.

Verification Result Vocabulary

The architecture now proves that Verification needs more than a simple boolean in some conditions.

Candidate result values include:

match
mismatch
unable_to_verify
incomplete_material
method_unavailable

These remain provisional until Validation and production testing determine whether any should be merged, renamed, or expanded.

Enumeration Unfrozen

Match

Conceptually, a match means the reviewed representation reproduced or validated the integrity material expected by the Integrity Reference.

Match = integrity consistency under the verified method

Mismatch

A mismatch means Verification completed but the reproduced or validated integrity material did not agree with the expected material.

A mismatch should trigger investigation rather than automatic assumptions about cause.

Possible causes: Source change · wrong representation · corruption · incorrect canonicalization · wrong Source input · Anchor error

Unable to Verify

Verification may be impossible even when no mismatch has been demonstrated.

missing Source Artifact
unavailable external service
unsupported method
missing historical proof
unavailable key material
incomplete provenance

These conditions should not be misreported as a mismatch.

Verification Result vs. Integrity State

A Verification Result records one Verification event. Integrity State describes the broader current integrity condition of the Integrity Reference.

Verification Result ≠ Integrity State

Lifecycle and Maintenance architecture will determine how repeated results influence Integrity State.

Separate Verification Record?

Anchor may later determine that significant Verification events deserve separately identified records rather than only embedded history.

Integrity Reference → verified_by → Verification Record

That object identity remains unfrozen. The first production workflow should prove whether separate Verification records create durable value.

Initial Verification vs. Reverification

Anchor should distinguish the verification performed during production from later Reverification events.

Initial Verification → confirms production construction
Reverification → tests continued integrity later

Whether these require different Controlled Values or procedure types remains unfrozen.

Verification and Source Change

A Source Artifact may legitimately change after the original Integrity Reference was created.

Verification must test the representation the Integrity Reference actually governs—not silently substitute the newest Source Version.

Original Integrity Reference → original governed representation
Later Source Version → separate evaluation

Verification and Corrections

A mismatch may reveal an Anchor error rather than a Source change.

If Anchor recorded the wrong digest, representation, method, timestamp, or other Anchor-owned information, Corrections architecture should govern the response.

Mismatch → investigate cause → do not silently rewrite

Verification and Provenance

Provenance provides the reconstruction instructions Verification depends on.

Provenance → how integrity material was produced
Verification → whether that process can still be reproduced or validated

Verification and Validation

Verification and Validation are separate operations.

Verification → Does the representation match the preserved integrity evidence?
Validation → Does the Integrity Reference satisfy Anchor's institutional and schema requirements?

A record may pass schema Validation but fail Integrity Verification, or Verify successfully while still violating an institutional Validation rule.

Verification Procedure Sequence

1. Identify Anchor Identifier and Anchor Version
2. Load Integrity Reference
3. Confirm Source / Representation context
4. Obtain Reviewed Representation
5. Reconstruct Canonical Representation
6. Identify applicable Integrity Method(s)
7. Reproduce / validate Integrity Material
8. Compare expected and observed material
9. Record method-level outcome(s)
10. Determine Verification Result
11. Preserve Verification event
12. Trigger investigation / Maintenance where required

Verification Principle

Verification should report what the evidence demonstrates and preserve uncertainty where the process cannot reach a valid comparison.

Reproduce faithfully. Compare precisely. Report only what the evidence proves.
Schemas → Provenance → Relationships → Controlled Values → Back to Anchor →
Verification should prove consistency without claiming more than the evidence allows.
