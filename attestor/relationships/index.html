Attestor · Advanced Architecture

Relationships

Relationships define the governed connections among Attestations, Trust Statements, evidence, source objects, prior statements, and canonical Suite objects.

Attestor uses relationships to preserve traceability and meaning across institutional boundaries without collapsing distinct objects into one record or allowing reference to transfer ownership or authority.

Relationship principle: Connection does not imply identity. Reference does not transfer authority.

Relationship Purpose

Relationships express governed connections among Attestor-owned objects and referenced sources. A relationship states how two objects are connected; it does not merge their identity, provenance, lifecycle, authority, or institutional ownership.

Attestation Relationships

An Attestation may reference source objects, be supported or challenged by eligible governed inputs, be evaluated by an Attestor evaluation, relate to other Attestations, and participate in correction or supersession. Its relationships must preserve the distinction between the assertion and the sources used to evaluate it.

Trust Statement Relationships

A Trust Statement must remain connected to the evaluation that produced it and to the supporting Attestation or Attestations. It may also relate to prior Trust Statements, source objects, corrections, versions, or other governed objects without inheriting their authority.

Evidence Relationships

Evidence is treated as governed supporting material or an authoritative reference, not automatically as a separate Attestor-owned canonical object. Relationships must therefore identify how evidence supports, limits, contradicts, or otherwise informs an Attestation or evaluation without converting evidence into a Trust Statement.

Source Object Relationships

Source objects retain their source identifiers, provenance, meaning, lifecycle, and authority. Attestor relates to them through governed references rather than duplicating them as Attestor records.

Prior Statement Relationships

A Trust Statement may have a governed relationship to an earlier Trust Statement when later review, correction, supersession, or changed conditions require continuity of history. The relationship must preserve both the prior object and the current governed state.

Suite Relationships

Attestor may relate to canonical objects from Atlas, Navigator, Certifier, Registry, Chronicle, Anchor, and Beacon. Each relationship preserves the canonical responsibility of the source institution.

Relationship Reviewability

A material relationship must be explicit enough to understand the source object, target object, relationship meaning, and direction where direction matters. Hidden or ambiguous connections must not carry normative meaning.

Canonical Relationship Vocabulary

The Controlled Values architecture established the initial relationship vocabulary. This page now defines the conceptual meaning and direction of those relationships. Exact field representation and cardinality remain Schema and Validation concerns.

supports → source object provides material support to target assertion, evaluation, or conclusion

references → source object explicitly identifies or cites target object without implying derivation or support

derived-from → source object was materially produced from target object or governed basis

evaluates → source evaluation acts upon target Attestation / assertion

results-in → source evaluation produces target Trust Statement

supersedes → source object becomes the governed successor to target prior object

corrects → source object or governed change addresses an error or material defect in target prior object

related-to → bounded non-specific relationship used only when a more precise canonical relationship does not apply

Relationship Direction

Normative relationships are interpreted from a source object toward a target object. Reversing the objects may change the meaning. Implementations must not assume every relationship is symmetric.

Evidence / Governed Input → supports → Attestation / Evaluation
Attestation → references → Source Object
Derived Object → derived-from → Source Basis
Evaluation → evaluates → Attestation
Evaluation → results-in → Trust Statement
New Object → supersedes → Prior Object
Corrective Object / Change → corrects → Prior Object

related-to ↔ may be non-directional only where architecture explicitly permits

Core Attestor Relationship Chain

The central Attestor process can be expressed as a governed relationship chain. Each step preserves the identity and authority of the participating objects while making the institutional lineage explicit.

Attestation → references → Eligible Governed Inputs
Eligible Governed Inputs → support / limit / conflict within → Evaluation Basis
Evaluation → evaluates → Attestation
Evaluation → results-in → Trust Statement
Trust Statement → derived-from → Governed Evaluation Basis

Distinct objects → Explicit relationships → Preserved lineage

Support Is Not Determination

The supports relationship records material support; it does not itself determine the evaluation outcome. Multiple supporting relationships do not automatically produce a supported Trust Statement, and a single conflicting or contradictory input may be material depending on scope, authority, provenance, and evaluation rules.

supports → Evidentiary / contextual relationship
supported → Evaluation outcome

supports ≠ supported
Relationship Count ≠ Evaluation Outcome
Relationship Presence ≠ Evidence Sufficiency

Reference Is Not Derivation

A reference identifies another object. Derivation states that an object was materially produced from another governed basis. These relationships must remain distinct because they carry different provenance and review implications.

references → “This object identifies or cites that object.”
derived-from → “This object was materially produced from that governed basis.”

Reference ≠ Derivation
Reference ≠ Support
Reference ≠ Authority Transfer

Supersession and Correction

Supersession and correction preserve governed continuity rather than erasing history. A superseding or corrective relationship must keep the prior object identifiable and distinguish the earlier state from the current governed state. Exact lifecycle effects are defined by Lifecycle and Versioning.

Prior Object → Remains historically identifiable
New / Corrective Object → Explicitly relates to prior object
Current State → Distinguishable from historical state

Correction ≠ Deletion
Supersession ≠ Historical Erasure

Suite Relationship Boundaries

Relationships to Suite objects preserve each institution's canonical responsibility. Attestor may cite, derive context from, or evaluate eligible information associated with those objects, but the relationship never converts the source object into an Attestor-owned object.

Atlas → Authoritative Intelligence
Navigator → Workflow Definition / Orchestration
Certifier → Certification Package
Registry → Satoshium Registry Record
Chronicle → Chronicle Entry
Anchor → Integrity Reference
Beacon → Discovery Signal / Discovery Metadata
Attestor → Trust Statement

Reference does not transfer authority.

Relationship Constraints

Not every relationship is valid between every object class. The vocabulary established here provides semantic meaning, while later Schemas and Validation architecture will define permitted source/target combinations, required relationships, cardinality, inverse representation where useful, and machine validation.

Relationship Meaning → Established here
Permitted Source / Target Classes → Schemas / Validation
Required vs. Optional → Schemas
Cardinality → Schemas
Inverse Representation → Relationships / Schemas as needed
Machine Enforcement → Validation

What Relationships Do Not Establish

A relationship expresses a governed connection. It does not independently establish truth, authority transfer, eligibility, evidence sufficiency, lifecycle state, validation, conformance, or a favorable evaluation outcome.

Relationship ≠ Identity
Relationship ≠ Authority Transfer
Relationship ≠ Eligibility
Relationship ≠ Evidence Sufficiency
Relationship ≠ Validation
Relationship ≠ Conformance
Relationship ≠ Evaluation Outcome

Advanced Architecture Position

The Relationships architecture now gives Attestor an explicit semantic graph connecting assertions, governed inputs, evaluations, conclusions, prior states, and external or Suite-owned source objects. Lifecycle and Versioning can now define how those relationships behave as governed objects change over time.
