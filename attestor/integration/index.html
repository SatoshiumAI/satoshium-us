ATTESTOR · OPERATIONAL INTEGRATION

Satoshium Attestor Integration

Attestor Integration defines how Attestor operationally participates in the Satoshium Suite by receiving, resolving, referencing, and evaluating governed inputs while producing its own canonical Trust Statements.

Integration answers a practical question: how do governed inputs enter an Attestor evaluation without losing their source identity, provenance, scope, status, relationships, or authority?

Canonical responsibility: Attestor → Trust Statement
Governing principle: Reference does not transfer authority.

Purpose

Attestor Integration establishes the operational relationships through which eligible governed information can participate in Attestations, evaluation, and Trust Statement production.

Integration Boundary

Integration connects systems and institutional objects. It does not merge their canonical responsibilities. Attestor governs its own processing and outputs while the source institution remains authoritative for the referenced object.

Reference-Based Operation

Where an authoritative object already exists, Attestor should resolve and reference that object rather than silently recreate it as an Attestor-owned record.

Evaluation Boundary

Receiving an input does not determine the Attestor conclusion. Eligible inputs must participate in Attestor's own rule-constrained evaluation before a Trust Statement is produced.

Governed Integration Flow

Attestor's established institutional integration relationship is:

Source Object → Resolve Reference → Preserve Context → Establish Eligibility → Attestation → Rule-Constrained Evaluation → Trust Statement

This flow is no longer merely conceptual. The first controlled production operation exercised it against real governed Suite objects. Technology-specific transport, authentication, retry, notification, and interface mechanics remain implementation choices unless separately adopted by a production specification.

Atlas Integration

Attestor may receive or resolve references to authoritative Atlas intelligence when relevant to an evaluation. Atlas retains authority over the intelligence; Attestor governs only its use within Attestor.

Navigator Integration

Navigator may define or orchestrate workflows in which Attestor participates. Navigator governs workflow definition and orchestration; Attestor governs its own evaluation and Trust Statement.

Certifier Integration

Attestor may resolve and reference Certifier Certification Packages and governed certification artifacts when eligible. The first controlled production operation did so with SC-CERT-2026-0001 as the primary governed matter. Certification authority remained with Certifier while Attestor governed Eligibility, Attestation, Rule-Constrained Evaluation, and its resulting Trust Statement.

Registry Integration

Attestor may resolve and reference Satoshium Registry records and their governed relationships. Registry retains authority over the registered record, identifier, status, and lifecycle.

Chronicle Integration

Attestor may resolve and reference Chronicle Entries when historical, event, or provenance context is relevant. Chronicle retains authority over the preserved historical entry.

Anchor Integration

Attestor may resolve and reference Anchor Integrity References when integrity context is relevant. Anchor retains authority over the Integrity Reference and its governing integrity model.

Beacon Integration

Attestor may resolve and reference Beacon Discovery Signals or Discovery Metadata when discovery context is relevant. Beacon retains authority over its discovery objects and lifecycle.

External Integration

Attestor may accept governed inputs from external systems when their source authority, provenance, scope, relevant state, permitted use, and evaluation-specific Eligibility can be established under Attestor rules.

First Production Integration Baseline

The first controlled production operation demonstrated a real Certifier-to-Attestor integration path centered on SC-CERT-2026-0001. Attestor resolved and evaluated the Certifier-owned Certification Package while preserving the canonical identities and authority of all referenced Suite objects.

SC-CERT-2026-0001 → Certifier-owned Certification Package
→ Eligibility determined under Attestor rules
→ ATT-2026-0001 created under Attestor authority
→ Rule-Constrained Evaluation conducted by Attestor
→ Evaluation Outcome → supported
→ TRST-2026-0001 created under Attestor authority

Referenced governed relationships → SREG-2026-0001 · CHR-2026-0001 · ANCH-2026-0001 · BEAC-2026-0001

Certifier authority remained with Certifier.
Registry, Chronicle, Anchor, and Beacon authority remained with their respective institutions.
Attestor authority applied only to its own Attestation, evaluation, and Trust Statement.

Integration Does Not Imply Automatic Conversion

A Certification Package does not automatically become an Attestation. A Registry record, Chronicle Entry, Integrity Reference, Discovery Signal, or other governed object does not automatically become a Trust Statement.

Integration makes governed information available for Eligibility determination. The established Attestation, Evaluation, and Trust Statement architecture separately governs assertion formation, Rule-Constrained Evaluation, and canonical conclusion.

Availability ≠ Eligibility ≠ Attestation ≠ Trust Statement

Interoperability and Integration

Interoperability defines what meaning, provenance, scope, relationships, status, and authority must remain intact when information crosses institutional boundaries. Integration defines the operational connection through which Attestor obtains and uses that governed information.

Interoperability → Preserve Meaning and Authority
Integration → Connect and Exchange
Rule-Constrained Evaluation → Produce the Trust Statement

Current Integration Position

Integration is established as both institutional architecture and exercised production capability. Reference Profiles, Eligibility, Authority, Provenance, Relationships, Evaluation, Lifecycle, Versioning, Validation, Conformance, Publication, and Production now govern the path by which Attestor receives and uses governed information without creating a parallel source-authority system.

A material change in an integrated source may trigger governed review, but it does not automatically determine correction, withdrawal, supersession, or creation of a new Trust Statement.

Exact APIs, transport mechanisms, authentication and authorization mechanisms, retry behavior, change-notification mechanisms, and digital-signature requirements remain technology-neutral implementation choices unless separately adopted by a production specification. Their continued openness does not make the institutional integration model incomplete.
